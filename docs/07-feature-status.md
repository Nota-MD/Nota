## 1. 现在真的能用（2026-09-22 开窗实测）

这一节列的是**有人在界面上点过**的东西。不是"代码写了"。

| 能力 | 怎么验的 |
|---|---|
| 应用启动、窗口打开 | 容器里 Xvfb + `import` 抓图，见 `docs/06` §5 |
| 插件发现与加载 | 侧栏「插件」页显示两个内置插件**都是「已加载」**；启动日志打 `[nota] 载入 2 个插件` |
| 新建文档 | 点「新建文档」→ 建出标签页 |
| 打字与即时渲染 | 打 `# 第一份 Nota 文档` → 渲染成一级标题；`**正文**` → 真的加粗 |

## 2. 缺陷清单

编号是**永久的**：修好之后把状态改成 `✅ 已修（日期）`，**不要删行、不要把号让给新条目**
——别处的注释与提交信息会引用这些号。

| 编号 | 状态 | 症状 | 根因与修法 |
|---|---|---|---|
| **BUG-1** | ✅ 已修（2026-09-22） | 插件的 `on_unload()` **从来没有被调用过** | `LuaPlugin::unload()` 从 `globals()` 里读 `__nota_module`，而 `run_entry()` 从来没往那儿写过东西。改成两头都用**命名注册表值** `nota_module`（用注册表而不是全局，是因为插件可以合法地把全局 `nota` 覆盖掉） |
| **BUG-2** | ✅ 已修（2026-09-22） | **没打开文件夹时，Git 插件显示「失败」**，而插件本身一个字都没写错 | `nota.git` 的 `working_dir()` 对"没有工作区也没有活动文档"直接抛 Lua 错误，而 Git 插件的 `on_load()` 结尾要刷一次状态——于是**环境问题被当成了插件故障**。改成：**调用错误**（传 `-C` 之类）抛错，**环境不具备**折成一张 `code != 0` 的结果表（`stderr` 里写原因）。插件侧那一次刷新再包一层 `pcall` |
| **BUG-3** | ✅ 已修（2026-09-22） | 插件**加载"成功"但一发事件就抛错**：`only alphanumeric, '-', '/', ':', '_' permitted for event names` | 清单里的插件 id 允许点（`nota.git`），而 **Tauri 的事件名不认点**。通道名是 `plugin:<id>:<名字>`，于是每一次 `emit` 都失败。加了 `manifest::channel_id()` 做归一化（**`.` 及其它不合法字符 → `-`；`-` 与 `_` 本来就在 Tauri 的允许集合里，原样保留**——⚠️ 本格的早期版本写成"`.`/`_`/其它 → `-`"，那是错的，`channel_id("a_b-c") == "a_b-c"` 有用例钉着），并在 `discover()` 里**检测归一后的撞名**（`nota.git` 与 `nota-git` 会撞，`nota_git` 与 `nota-git` 不会）：撞了就把后到的那个直接判失败，把话说在当面 |
| **BUG-4** | ✅ 已修（2026-09-22） | `Ctrl+W` 关文档时用的是**陈旧的闭包** | `App.tsx` 里 `closeDoc` 定义在快捷键 `useEffect` **之后**，且没进依赖数组，于是快捷键一直抓着首次渲染那一版。把 `closeDoc` 的 `useCallback` 提到 effect 之前并加进依赖 |
| **BUG-5** | ❓ 待查 | **中文输入法（IME）组合态**未实测 | ProseMirror 的 IME 处理是成熟的，但中文输入是 Nota 的主力场景，**这条要专门验一遍**。见 backlog 第 24 项 |
| **BUG-6** | ⬜ 未修 | **切标签时后端的「活动文档」不跟着变**：`TabBar.onSelect` 只 `setActiveId(id)`，**从不调 `api.doc.setActive`**。于是后端的活动文档只被 `new`/`open`/`close` 改过。⚠️ **后果对插件是实的**：用户点了标签 A 在看 A，`nota.document.get_text()` 却返回**最后一次新建/打开的那份**——AI 助手插件按这个路径写回，就会**改错文档**。修法：`onSelect` 里同时调 `api.doc.setActive`（或在 `activeId` 的 effect 里统一同步） | 前端单方面漏了一枪。后端命令 `nota_doc_set_active` 早就有了，`ipc.ts` 里也声明了 `api.doc.setActive`——只是**没有任何调用者** |
| **BUG-7** | ⬜ 未修 | **`applyTheme` 的退订函数被丢掉**：`App.tsx` 里写的是 `if (settings) applyTheme(settings);`，**没有接返回值**。`ui_mode = "auto"` 时每次 `settings` 变化都会再挂一个 `matchMedia` 监听，旧的**从不移除** | effect 漏了 `return` 清理函数。功能上不致命（`paint()` 幂等），但监听器累积。修法：`return () => applyTheme(settings)`，并把 `applyTheme` 返回的退订函数往上抛 |
| **BUG-8** | ✅ 已修（2026-09-22） | **只申请 `ui.menu` 的插件拿不到 `nota.ui`**，调 `register_menu` 直接 `attempt to index a nil value`。`ui.menu` 这条能力**形同虚设** | `lua/api/mod.rs` 的判据写的是 `ui.notify \|\| ui.panel`，**漏了 `ui.menu`**；而 `ui.rs` 表内三个方法又各自判一次。两层判据**相乘** → 只申请 `ui.menu` 的插件连表都拿不到。两个内置插件都申请了 `ui.panel`，所以一直没暴露。**修法（已落地）**：把判据剥成纯函数 `装_ui吗()`，由 `const UI能力: [Capability; 3]` 驱动——**外层判据和 `ui.rs` 里那三处由同一个数组产生，漏一项就不可能悄悄溜过去**。加了 4 条回归用例：每条 `ui.*` 能力单独装表、没申请不装表、**`UI能力` 与 `ui.rs` 里的判据个数对得上**（用 `include_str!` 数 `manifest.has(Capability::Ui` 的出现次数）、以及能力的 serde 名与 `parse()` 同口径。用例数 32 → **36** |
| **BUG-9** | ⬜ 未修 | **每个未命名文档的标题都是「未命名 0」**：新建两份未存盘、且正文还没有标题的文档，标签页上两份**同名** | `derive_title(text, path, untitled_index)` 本身收序号，但**四个生产调用点全部传字面量 `0`**（`document/mod.rs` 第 192/212/228/254 行）；只有用例传了 1/7/3。序号从来没有真的递增过。**修法：`DocumentStore` 里存一个计数器，新建时 `+1`**（注意还有 `docs/09` 的映射要同步） |
| **BUG-10** | ✅ 已修（2026-09-22） | ⚠️⚠️ **Lua 插件的沙箱第一道闸是假的**：一个**只申请 `ui.notify`** 的插件可以 `os.execute("rm -rf ~")`、`io.open("/etc/shadow")`，**绕过全部能力围栏**。所谓"能力"曾经只是装饰 | **`Lua::new()` 的 "safe" 不等于"没有 io/os"**。mlua 0.12.1 的 `src/stdlib.rs`：`ALL_SAFE = StdLib((1 << 30) - 1)` 含第 0–29 位，而 `IO`=bit2、`OS`=bit3、`PACKAGE`=bit8 **全在里面**，只有 bit31 的 `DEBUG` 被排除。`new_with` 里真正做的只有 `mark_safe()` + `disable_c_modules()`——**"safe" 指的是"不能加载 C 模块"**。实测（与本项目同 feature）：`os.execute("touch /tmp/x")` 真建出文件、`io.open("/etc/hostname")` 真读到 `toolbx`、`require` 的唯一失败原因是 `can't load C modules in safe mode`。**修法：不再依赖 `Lua::new()` 的默认值**，`硬化的_lua()` 用 `new_with` 只开 `coroutine`/`table`/`string`/`utf8`/`math`，再把 `io`/`os`/`package`/`require`/`loadfile`/`dofile`/`debug` 逐个置 `nil`（⚠️ `loadfile`/`dofile` 属于**无条件加载的 base 库**，`StdLib` 关不掉，必须显式抹）。加 4 条用例钉住，测试数 36 → **40**。**教训：别把库的 `safe` 字面当安全承诺**——"safe" 是它自己定义的口径，写在源码里，只能自己去读 |
| **BUG-11** | ⬜ 未修 | **打包（release）后一个内置插件都没有**：`tauri.conf.json` 的 `bundle` 段**没有 `resources` 键**，而 `paths.rs:48` 找的是 `resource_dir.join("plugins")` | 开发期走的是仓库目录，所以看不出来；装出来的包里那份 `plugins/` 根本没被塞进去，且 release 下也不走 `debug_assertions` 分支。**修法：`bundle.resources` 里带上 `plugins/`**，并验一次真装出来的包。**排期见 backlog 第 34 项** |
| **BUG-12** | ⬜ 未修 | **文件刚打开就显示「已修改」**：状态栏明写 `/tmp/demo.md ● 已修改`，而用户一个字都没动过。2026-09-22 在 Xvfb 里实测（打开 `docs` 外的 `/tmp/demo.md`） | 打开文件走 `api.doc.open()` → 前端 `setMarkdown()` → Milkdown 的 `listenerCtx.markdownUpdated` 触发 → `onChange` → 标脏。**根因待查**，两个候选：① 序列化回来的文本与原文并非逐字节相同（`markdown !== prev` 成立），② `setMarkdown()` 之后那一次 listener 回调本来就不该算「用户编辑」。⚠️ 后果不止是状态栏难看：**关窗口 / 切文档时会弹「未保存」**，用户会以为文件被动过。⚠️ 还有一个伴生现象：**标签页上的脏点与状态栏不同步**（同一次打开，标签页没点、状态栏写了「已修改」） |
| **BUG-13** | ✅ 已修（2026-09-22） | **四条宿主事件里，有两条发出去没人接**：后端 `nota:plugin-panel` 与 `nota:plugin-menu` 都在 `emit`，而前端只订了 `nota:notify` 与 `nota:document-changed`（`App.tsx:117`/`122`）。⚠️ **`ipc.ts` 里连类型都写好了**（`PluginPanelPayload`/`PluginMenuPayload`）——所以"接口齐了"这个观感是假的，它恰恰是**最容易骗过核对的一类**。<br>⚠️ **措辞要准：这个事实此前是记过的**（`docs/02:2102` 白纸黑字写着「`pluginPanel` / `pluginMenu` 今天没有任何订阅者」）。它没进缺陷清单，也没有人问过"那要怎么才能接上"——**而后者才是本条的真正内容** | ⚠️ **它比 BUG-6 更值得记，因为"加一句 `listen`"是错的修法。** 面板与菜单都在**插件加载时**（启动阶段）注册，前端订阅在**挂载之后**——直连必漏，且**漏得安静**：界面看着好好的，只是永远空着。本仓已有的正确范式是**注册进插件的 Lua registry、宿主按需拉**（`nota_commands`）。**修法（已落地）**：两条 `emit` **直接删掉**，改成 `nota_panels`/`nota_menus` 两个 registry 值 + `nota_plugin_panels`/`nota_plugin_menus` 两条命令；`ipc.ts` 里那两条事件名与两个 `Payload` 类型一并删除（留着就是下一次踩的坑）。`location` 默认值 `"sidebar"` → `"right"`。加 5 条回归用例，**故意让写的一侧（`lua/api/ui.rs::面板表`）与读的一侧（`plugin/mod.rs::读面板`）都参与**——只为这个病灶正是"两头各写各的"，只测一头永远测不出来。用例数 40 → **45**。<br>⚠️ **另记一条被推翻的设计**：`lib.rs::nota_frontend_ready` 的注释里原本写着"当场发 + 记账 + 前端起来后**重放**"。**那个设计是错的，不是没做完**——它把面板清单变成**两个真相源**（前端的事件账本、插件自己的注册表），重放漏一次或前端不是幂等的就静默分叉，还是同一个病。已把那段注释改写成"为什么重放是错的" + 这个命令现在还剩什么用 |
| **BUG-14** | ✅ 已修（2026-09-22） | **两个内置插件都声明了位置为 `sidebar` 的面板**，而左侧栏第三页早已搬到右边（`docs/04` §2.2b）——于是 `plugins/ai` 与 `plugins/git` 声明的面板**哪儿都不会出现** | 旧默认值留下的化石。`plugins/git/main.lua:164` 与 `plugins/ai/main.lua:134` 都写着 `location = "sidebar"`，而 `Sidebar.tsx` 已经删掉了装插件的那一页。**这个 bug 是修 BUG-13 时才暴露出来的**：接上以后界面上立刻多出一组「没有落脚处」，把 `AI / sidebar` 列了出来——**新代码自己把旧数据的问题报了出来**，这也是那组"不静默丢掉"的设计当场收回的成本。修法：两处都改成 `location = "right"`（现在等于默认值，写出来只为可读） |

> **BUG-3 的教训值得单独记**：它属于"**加载成功、静默失效**"那一类——
> 插件列表里一切正常，错误只在**第一次发事件**时出现，而且发事件是插件的
> `on_load` 里做的事，所以现象是"这个插件有时好像没反应"。
> 静态看代码完全看不出来。**这类 bug 只有真跑一次才抓得到**，
> 而它正是用户那句「尽量少问、自行决定」之下最容易漏的一类。
> 抓到它的过程也记一笔：BUG-2 修完之后我加了 `pcall` + `nota.log.warn` 兜底，
> **是那条兜底日志把错误打出来的**——没有它，BUG-3 会继续潜伏。
>
> **BUG-8 的教训是另一类，也值得单独记**：它是**"两层判据相乘"**——`ui.rs` 里每个函数
> 自己判一次能力，`api/mod.rs` 再判一次"表装不装"。两处都对才通了路，而**任一处漏一项，
> 那项能力就是死的**。这种结构的坑在于：**每一层单独看都像是对的**，写第二层的时候
> 脑子里想的是"我列了几个了"，而不是"全集有几个"。修法没有停在"补上漏的那一项"，
> 而是**让两层由同一个数组产生**（`const UI能力`），并加一条用 `include_str!("ui.rs")`
> 数判据个数的用例——**Rust 没有反射，这条推不出来，所以退一步钉"数量"**：
> 谁往 `ui.rs` 加了第四个 `ui.*` 判据，用例就红，于是被提醒回来改。
> ⚠️ **这不是完备的保证**（数量对得上不等于名字对得上），但比"靠人记得"强，
> 而且**下次加能力时它一定会响**。真正管用的是"两层同源"这个改法本身。
