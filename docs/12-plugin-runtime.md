## 1. 为什么是 Lua

### 1.1 一句话

因为**插件的作者不是 Rust 开发者**。一个 Markdown 编辑器的插件生态，
主力是"想把某件每天重复的小事自动化"的人——他愿意写二十行脚本，
不会愿意装一套 Rust 工具链、学一遍生命周期、为改一个字符串重编 30 秒。

### 1.2 与其它方案的对比

| 方案 | 优点 | 失败原因 |
|---|---|---|
| **Lua**（选它） | 解释器小、嵌入成本低（mlua 一行 `Lua::new()`）、**纯文本单文件、改完存盘就是新版本**、语法足够写"解析 git 输出"这种活 | 动态类型：插件作者写错字段名要到运行期才知道；⚠️ 另外 mlua 的"安全子集"**自带完整文件系统与进程能力**（§5）——**本仓已自己收紧，见 `docs/07` BUG-10** |
| 进程内 C ABI（`.so`） | 最快、无障碍调宿主 | 要编译工具链 + 稳定的 C ABI + **段错误就是宿主的段错误**。这是 Folio 走的路（`AGENTS.md` §1 那张对比表），它要的是性能与原生 GTK 控件的接入；Nota 这边没有这个诉求 |
| WASM | 隔离最干净（内存沙箱 + 指令计数都是白送的） | 要引入一整个运行时，宿主 API 需要先序列化过界、再在 wasm 侧重新做一套绑定；**"插件就是一串字符串"这个最简单的卖点没了** |
| 嵌入式 JS（QuickJS） | 心智与前端一致 | 宿主里多一个 JS 引擎，而**前端 WebView 里本来就有一个 JS**——两边的 `nota` 不是同一个对象，插件作者容易混淆。文档需要花半页解释"插件里的 JS 跑在 Rust 里，不是前端那个 JS" |
| 纯声明式（只留 TOML） | 没有代码就没有沙箱问题 | 表达力不够。`plugins/git/main.lua` 要按 `-z` 分割 NUL、按状态字母归类、拼命令行——**这是逻辑，不是配置** |

⚠️ **另有一条不好写进表里的理由**：工作区里的 Folio 也用了 Lua
（见 `docs/01-architecture.md` 的家族说明）。**同一位作者的两个项目用同一套插件语言**，
意味着插件作者的心智模型、遇到过的问题、写文档的口径都能复用。这条对"选什么语言"的影响
通常比技术指标大。

### 1.3 代价（选之前要知道的）

| 代价 | 具体表现 |
|---|---|
| **动态类型** | 能力名拼错、命令名拼错、函数签名记错，**都在运行期才知道**。宿主能做的只有把错误信息写清楚（`docs/11` §2.2、§6.5） |
| **一门新语言要学** | 对只写前端/后端的用户，Lua 的表/元表/`pcall` 是需要另学的一套东西。所以 `plugins/` 里那**四个**内置插件（Git / AI 助手 / Slidev 演示 / **写作统计**）**同时是样例**——照抄比读文档快。⚠️ 2026-09-26 从三个变四个：写作统计是**最小**的一个（它只申请两条能力），拿它入门比拿 Git 那个 999 行的快 |
| **宿主 API 要手工维护两层判据** | 每加一个 `nota.*` 成员，就要在"表装不装"和"成员装不装"两处各判一次能力。⚠️ **BUG-8 就是这个手工维护漏掉的一项**（§4.3） |
| **同进程**（§5、§6） | 故障隔离做到了；安全隔离**曾经没做到，2026-09-22 起做到了**（BUG-10）。⚠️ 但**内存与死循环仍不隔离** |

## 2. 一个插件一个 `Lua` 状态

### 2.1 事实

```
LuaPlugin { manifest, lua: Lua, state, has_unload }     // src-tauri/src/lua/mod.rs 的 `struct LuaPlugin`
```

每个插件**自己一个** `Lua`——`LuaPlugin::load()` 里调 `硬化的_lua()`（**曾经是
`Lua::new()`，见 §5 与 `docs/07` BUG-10**）。不是共享池、不是按需创建：
`rejected()`（撞名被拒的插件）甚至都要先建一个空状态，
代价换的是"两种失败对界面来说长得一样"。

### 2.2 ⚠️ 这是与 Folio **有意相反**的设计

| | Folio | Nota |
|---|---|---|
| 插件形态 | 进程内 C ABI（`.so`） | Lua 状态 |
| 隔离粒度 | **没有隔离**（无沙箱） | **Lua 状态** |
| 宿主 API 可见性 | 插件能链到的符号都能调 | 按能力**装配**（§4） |
| 插件崩了 | **宿主一起死** | 这个插件判失败，宿主继续跑 |

（上表前两行的对比照 `AGENTS.md` §1「与 Folio 的关键差别」。
那条表还提醒了一句：**不能照搬那边的结论**——这里正是它指的地方。）

`src-tauri/src/lua/mod.rs` 的模块注释把这条对比写进了源码：

> 整个 chunk 用 `pcall` 包着跑——**插件炸了不能带走宿主**
> （这条与 Folio 的 C 插件相反：那边同进程无沙箱，插件的段错误就是宿主的段错误）。

### 2.3 收益（照 `lua/mod.rs` 模块注释里"一插件一状态"那三条）

1. **隔离**：一个插件把脚本写崩（栈溢出、抛错），影响不到别的插件，也影响不到宿主。
   ⚠️ 注意原文里"栈溢出"这个词——实际上 Lua 层的栈溢出是被 `pcall` 变成错误的，
   而 **C 栈溢出 / OOM / `os.exit()` 不在隔离范围内**（§5）。
2. **能力放行是天然的**：`nota.document` 这张表**只在插件申请了
   `document.read`/`document.write` 时才存在**——不是"存在但调用时报错"。没申请
   `process.git` 的插件，`nota.git` 那张表就是 `nil`，"写不出来也绕不过去"。
3. **卸载 = 丢掉这个 `Lua`**：不用做引用计数、不用管谁还拿着回调。
   ⚠️ 2026-09-25 起这条**天天在用**：用户的「停用」就是一次真卸载
   （`LuaPlugin::disabled`，见 `docs/11` §1.6.7），不只是退出时那一次。

第 2 条是这套设计里收益最大的一处，**但它的前提在 §5 被推翻了**——
按能力装配管的是"宿主递给插件什么"，管不了"插件自己能拿什么"。
模块注释里那句"脚本能做的事 = 清单申请到的事，没有旁路"**曾经是假的**
（`os.execute` 就是旁路）——**2026-09-22 收紧标准库之后它才成立**（§5、BUG-10）。

### 2.4 代价

| 代价 | 说明 |
|---|---|
| **内存**：每插件一份解释器 + 一份标准库 | 内置插件只有两个，感知不到；⚠️ **没有上限、没有池化、没有共享只读段**。装几十个插件的用户会看到内存随插件数线性上涨 |
| **没有跨插件的共享内存** | 插件之间的协作只能过宿主（而宿主那半还没实现，见 `docs/11` §7） |
| **重复建表** | 每个插件的 `nota.*` 都重新构造一遍（`api::build`）。命令表、面板表、菜单表也都是每插件一份 |
| **编译好的 chunk 不能共享** | 每个状态都从头 `load` 一次入口脚本 |

⚠️ **代价的量级判断**：两份内置插件一共不到 350 行 Lua。这个取舍今天是明显划算的
（用一点内存换掉整个 C ABI 稳定性问题）；**它是否划算取决于插件数量**，
所以这是将来该回看的一条，不是永久结论。

## 3. 为什么必须开 mlua 的 `send`

```toml
# send：Lua 状态要放进 Tauri 的 managed state（跨线程），不加这个 feature
#       编译期就会因为 Lua 不是 Send 而卡住。
mlua = { version = "0.12", features = ["lua54", "vendored", "serialize", "send"] }
```

（`src-tauri/Cargo.toml` 的 `mlua = …` 那一行及其上方注释。）

### 3.1 精确的因果链

1. `LuaPlugin` 存在 `PluginHost` 里；
2. `PluginHost` 进 Tauri 的 managed state（`lib.rs` 里 `app.manage(...)`）；
3. Tauri 的 managed state 要求 `Send + Sync`；
4. **不开 `send`，`mlua::Lua` 不是 `Send`** → 第 2 步编译不过。

mlua 对这个 feature 的定义（`README.md`）：

> `send`: make `mlua::Lua: Send + Sync`
> (adds `Send` requirement to `mlua::Function` and `Send + Sync` to `mlua::UserData`)

⚠️ 注意后半句：它**附带把要求加到了 `Lua` 之外的类型上**。所以哪天要给插件做
`UserData`（把 Rust 结构体暴露成 Lua 对象），那个结构体也得是 `Send + Sync`。
这是开了这个 feature 之后才生效的约束，加新类型时会被编译器提醒。

### 3.2 ⚠️ `send` 不是"线程安全"，只是"能跨线程移动"

`send` 是**类型层面的开关**，不是运行时锁。它让 `Lua` 可以放进 `Mutex` 里被多个线程
持有，**不等于**可以并发地进入同一个 `Lua`。

真正管住并发的是这三样，都是本仓自己写的：

| 手段 | 在哪 |
|---|---|
| `Arc<Mutex<DocumentStore>>` / `Arc<Mutex<Settings>>` / `Arc<Mutex<Option<PathBuf>>>` | `HostContext`（`lua/mod.rs` 的 `struct HostContext`），`HostContext` 本身 `#[derive(Clone)]`——每个闭包克隆一份，**里面共享的是同一批 `Arc`** |
| **锁序不变量**：`plugins → documents → settings`，只能从左往右 | `lua/mod.rs` 的 `struct HostContext` 文档注释与 `state.rs` 的文件头各写了一遍 |
| 命令调用走 `PluginHost` 的锁 | `plugin/mod.rs` |

⚠️ **锁序那一条值得单独说明**：违反它的后果是**死锁，而且是最难查的那种**——
平时不触发，只在插件的 Lua 回调（持着 `plugins`，要读 `documents`）和存盘流程
（持着 `documents`，要读 `settings`）**碰巧同时跑**时才卡住。
它不会报错，只会让界面停在那儿。

### 3.3 `vendored` 是另一个"没得选"

```toml
# vendored：把 Lua 5.4 源码一起编进来，不依赖系统 liblua（容器里也没有）。
```

（`Cargo.toml` 的 `vendored` 那行注释。）这条不需要解释得太细：**容器里没有系统 liblua**，
所以不 vendored 就是构建直接失败。⚠️ 附带的好处是**版本锁死**——
`lua54` 指的是 Lua 5.4 的语义，宿主带的是自己编的那一份，
不会因为用户机器上的 liblua 是 5.3 而行为不同。

## 4. 沙箱的墙画在哪：**按能力装配**，不是黑名单

### 4.1 口径

`lua/api/mod.rs` 的模块注释（「一条硬规矩：**按能力装表，不装空壳**」那段）把口径写得很清楚，两层：

1. **按能力装表，不装空壳。** 没申请 `document.read`，`nota.document` 就是 `nil`——
   不是"存在但调用时报错"。理由：前者让插件作者**在开发期**就发现问题，后者写完才失败；
   也让"权限"变成一道**结构上的隔离**，而不是一句运行时的检查。
2. **每个能力对应一张表的一部分**，表里的成员各自再判一次。

一个推论值得单独说：**没有"删全局变量"这道工序**。
宿主不往 Lua 里塞危险东西、也就不需要去删什么——
黑名单的毛病是"默认开、漏一个就是一个洞"，而且事后审计得逐行读代码才知道谁有什么权限；
白名单是"默认关、显式开"，权限清单就是清单文件本身。

⚠️ **但这个口径有个隐含前提：墙外的世界是空的。** 如果 Lua 状态里已经有一整套
文件系统与进程能力，那么"删全局变量"这道工序不是"不必要"，而是**"还没做"**——
而 `Lua::new()` 给的正是那样一个世界。§5 是证据，**本仓后来就把这道工序补上了**
（`硬化的_lua()` 里那个 `必须为空的全局` 循环）。

### 4.2 两层判据

| 层 | 判据写在哪 | 内容 |
|---|---|---|
| **表装不装** | `lua/api/mod.rs` 的 `fn build()` 里那一串 `if manifest.has(…)` | `document`（`document.read` 或 `document.write`）、`fs`（`fs.read` 或 `fs.write`）、`git`（`process.git`）、`ui`（`ui.notify` 或 `ui.panel` 或 `ui.menu`——三条都在，见 §4.3）、`devserver`（`process.devserver`）、`http` / `settings` / **`data`**（各自的单项能力；`data.own` 2026-09-27 加，⚠️ 它**没有第二层**——那四个函数围的是同一个目录，见 `docs/13` §16.2） |
| **不需要能力的那几张** | 同一个 `build()` 里，**没有 `if`** | 身份三项 `version` / `api_version` / `plugin_id`、`log` / `command` / `event` / **`diff`**（2026-09-24 加的：`nota.diff` 是**纯函数**——一段文本进、一段文本出，不碰文档不碰磁盘，拿它做不出清单之外的事）、**`i18n`**（2026-09-25）、**`time`**（2026-09-27 加的：只把系统时钟报一遍，不读文档不读磁盘——⚠️ 时区偏移是"这台机器此刻的本地时间"的副产品，不是"用户在哪"，见 `docs/13` §16.1） |
| **表里成员装不装** | `document.rs` / `fs.rs` / `ui.rs` 各自开头 | 例如 `ui.rs` 的 `build()` 里三处判据各守一个成员：`UiNotify` → `notify`、`UiPanel` → `register_panel`、`UiMenu` → `register_menu` |

**两层是相乘的**：只申请 `ui.panel` 的插件，`nota.ui` 表存在、`register_panel` 存在，
但 `register_menu` 是 `nil`。

⚠️ **所以"表装不装"这层的判据必须把该表下面的**每一条**能力都列上。**
这是本节唯一一处**手工维护**的地方，也是唯一一处漏过东西的地方（§4.3）。

### 4.3 ⚠️ BUG-8：第一层曾经漏了一格（已修）

第一层那行条件**曾经**是：

```rust
if manifest.has(Capability::UiNotify) || manifest.has(Capability::UiPanel) {
    set(nota.set("ui", ui::build(lua, manifest, ctx)?), lua)?;
}
```

**漏了 `Capability::UiMenu`**，而 `ui.rs` 里 `register_menu` 那一个成员是**按 `UiMenu` 装的**。
于是两层判据对不上：

- 插件**只**申请 `ui.menu` → `nota.ui` 是 **`nil`** →
  `nota.ui.register_menu{...}` 报 `attempt to index a nil value (global 'nota.ui')`。
  **`ui.menu` 这条能力形同虚设。**
- 申请了 `ui.menu` **加** `ui.notify` 或 `ui.panel` → 一切正常。

两个内置插件都申请了 `ui.panel`（`plugins/git/plugin.toml`、`plugins/ai/plugin.toml`），
所以一直没暴露。

#### 修法是"两层同源"，不是补一个 `||`

**✅ 已在 2026-09-22 修掉**。做法不是直接补一个条件，而是让**第一层的判据由一张能力
清单产生**，并且让那张清单与 `ui.rs` 里的判据**数量挂钩**——这样以后不会再漏：

```rust
/// 装 `nota.ui` 这张表需要哪些能力。
/// ⚠️ `ui.rs` 里每多一个 `manifest.has(Capability::Ui…)`，这里就要多一项。
/// 两处是**相乘**的关系：里面那个判据决定"表里有没有这个函数"，
/// 外面这个决定"表本身在不在"。漏一个就是 BUG-8。
const UI能力: [Capability; 3] = [Capability::UiNotify, Capability::UiPanel, Capability::UiMenu];

/// `nota.ui` 这张表装不装。**纯函数**，单独剥出来是为了能被用例钉住。
fn 装_ui吗(manifest: &Manifest) -> bool { UI能力.iter().any(|c| manifest.has(*c)) }
```

（`api/mod.rs` 的 `const UI能力` 与 `fn 装_ui吗`。剥成纯函数的原因写在注释里：`build()` 要真的 `AppHandle`、
构造不出来，而这条判断是纯的，正是最该被用例钉住的那一条。）

**同批加的 4 条回归用例都在 `lua::api::tests`：**

| 用例 | 钉住什么 |
|---|---|
| `每一条_ui_能力都能单独装出_nota_ui` | 遍历 `UI能力` 逐项造清单 —— **BUG-8 的回归** |
| `没申请_ui_能力就不装_nota_ui` | 反向：一个 `ui.*` 都没申请就不该有表（按能力装表、不装空壳） |
| `ui_能力清单要和_ui_rs_对得上` | `UI能力` 的项数 == `ui.rs` 里 `manifest.has(Capability::Ui` 的出现次数。⚠️ **Rust 没有反射，这条推不出来，所以退一步钉"数量"**——谁往 `ui.rs` 加第四个 `ui.*` 判据，它就会失败 |
| `能力的_serde_名字与_parse_说同一套话` | `#[serde(rename)]` 与 `Capability::parse()` 的两套名字必须同口径 |

**测试数因此从 32 条变成 36 条**（计数只在 `docs/06` 记）。
`docs/07` 的 **BUG-8** 登记的就是这条缺陷，编号永久保留、状态列改成已修。

📌 这条附带留了个**方法论教训**（`docs/07` §4 的漂移登记表里记的是同一次事故）：
核对时只 `grep -n` 到下一行的 `set(...)`、**没看上一行的 `if`**，就会得出
"无条件调用、文档有误"这种**完全相反**的结论。判断"这里没有条件"必须看上下文几行。

### 4.4 ⚠️ 两张假表的历史（已于 2026-09-24 结清）

`nota.http` / `nota.settings` 在 2026-09-24 之前是**故意装出来的假表**：
用 `__index` 元表兜住任意方法名，**任何一次调用都抛**一句带文档条目号的错误。

**为什么当时给假表而不是不给**：给的是**线索**。有了它，插件作者写
`nota.http.get(...)` 立刻拿到「网络请求尚未实现（见 docs/07 第 12 项）」；
没有它，拿到的是 `attempt to index a nil value`——后者会让人**误以为是自己的能力没申请对**，
从而排查很久。

**这个做法在当时是对的，但它只适合临时采用。** 空壳终究是空壳：AI 插件因此只能预览、
存不住密钥，"联网"那半等于没有。**本轮（`docs/07` 第 12、13 项）两样都真做出来了**
（`lua/api/http.rs`、`lua/api/settings.rs`），`not_implemented()` 与它那套元表
已经删掉——`api/mod.rs` 里只剩一段注释记着这件事，因为**"当时为什么这么做"值得留下，
"这么做"不值得**。

### 4.5 插件设置为什么不加密

用户的密钥就存在 `~/.config/nota/plugin-settings/<id>.toml`，**没有加密**。
这是有意的取舍，也不打算以后补上——理由如下，**改动这个决定之前需要先读完本节**。

**它能挡住谁**：同机器上的其他用户（文件 0600、目录 0700），
以及"设置被无意间贴进 issue"（面板上的 `secret = true` 让输入框遮屏）。
这两件是真实的、经常发生的。

**它挡不住谁**：能读该账号文件的任何人或程序。**而加密也挡不住**——
插件运行时要拿明文去发请求，密钥就必须能在**进程内存里**被解出来，
而解密用的那把钥匙也只能存在同一个账号读得到的地方。
钥匙与密文在同一处，能挡住的仍然只有读不到该账号文件的人。
**加密在这里换来的是"看起来更安全"，代价是一个可能被丢失的密钥文件
（丢了就是所有插件设置全部读不出来）。**

**真正该做的两件事，是另外两件**：

| 事 | 状态 |
|---|---|
| **限制谁能读** | ✅ 文件 0600、目录 0700。这是唯一一条真正有效、且不依赖用户操作的防线 |
| **让密钥别到处跑** | ✅ `settings.own` 只能读**自己那一个文件**（`build()` 拿到的是本插件的 id），所以 AI 插件拿不到 git 插件的设置 |
| **让插件的数据别互相串** | ✅ `data.own` 只能读**自己那一个目录**（`~/.local/share/nota/plugin-data/<本插件 id>/`，2026-09-27 加）。⚠️ 它是**第三块**能碰磁盘的地方，与 `settings.own` 不是一回事（那边是"用户该能改的偏好"、在 `config`；这边是"插件自己写的账"、在 `data`），与 `fs.*` 也不是（那边围的是**用户的工作区**）。三块互相独立，见 `docs/13` §16.2 |
| 上系统密钥环（libsecret / Keychain） | ❌ **不做**，理由见下 |

**为什么不上系统密钥环**：那会把"插件设置"从一个纯文本文件变成一个**依赖桌面会话**
的东西——无头环境、SSH、容器里全都拿不到；解密失败时的症状是"设置无故消失"。
它还要求每个用户装并解锁一个密钥环服务。**对"存一个 OpenAI key"这件事，代价远大于收益。**
哪天插件要存的是能直接动钱的凭据，这条要重新判一次——那时也应该是**插件自己**
去要密钥环，而不是把整张 `nota.settings` 变成密钥环。

⚠️ **所以文档和界面上都不该称它"安全"。** 该说的是原话：**明文、0600、
只给这个插件看**。用户有权知道这一点再决定填不填。

### 4.6 面板内容：**一次拉**，不是一个频道

面板这条路被拆成了**两件不同的事**，混起来就是 BUG-13：

| | 声明 | 内容 |
|---|---|---|
| 是什么 | "我有这么一块面板，叫 Git" | "它此刻长这样" |
| 谁写的 | `nota.ui.register_panel` / `register_menu` | `render` 函数的返回值 |
| 什么时候发生 | `on_load` 里**一次** | **每次有人要就现跑一遍** |
| 怎么到界面 | 前端挂载后 `nota_plugin_panels` **拉** | `nota_plugin_panel_content(plugin, id)` **拉** |

两条命令**都是 `async` + `spawn_blocking`**（`commands/plugin.rs`）：`render` 里
常常要起 `git status` 子进程、发 HTTP 请求，跑在主线程上就是冻界面。

**那 `nota.ui.refresh("ai")` 是什么？** 它只做一件事：往界面发一条通知
「内容变了，去重拉一次」（前端收到 `nota:plugin-panel`，然后调上面那条
`panel_content`）。⚠️ **它是一条"失效通知"，不是内容的通道**——
谁都不该往这条事件里塞内容。判据很简单：**把这条事件整个丢掉，面板打开时
仍然显示正确的东西**（因为打开时本来就会拉一次）。丢掉它就显示不出来的设计，
说明内容被存了两份。

⚠️ **`nota.ui.refresh` 的代价是每次都要重跑一遍 `render`**，而 `render` 里通常是
一个子进程。所以它不适合在循环里调用，也不会顺带更新别的东西。

**⚠️ 2026-09-26 多了一档：「跟着时间自己动」（`live`）。** 上面那三个时机都是"发生了什么事"，
没有一条是"**时间过去了**"——而"实时"要的正是那一条。现在面板可以声明
`register_panel{ live = true }`（`lua/api/ui.rs`），宿主那边由 **`heartbeat.rs`** 每秒发一条
**同一个** `nota:plugin-panel`（不是新通道、也不是内容通道）——⚠️ **声明了才会被叫**，
没声明的一律不受影响。

三条代价，写插件的人必须知道：

1. ⚠️ **它的 `render` 每秒被重跑一次。** §4.7a 那句"面板的 `render` 里只许问'现在知道什么'、
   不许做'现在去查一下'"在这里从**经验**变成**硬约束**：一个 `live` 面板里跑一次
   `git status`，就是每秒起一个子进程——而且是在握着 `plugins` 锁的时候跑的（§4.7），
   一秒一次地把**别的插件**堵在后面。
2. **它不是定时器。** 插件那边仍然没有 timer、仍然收不到宿主事件，代码还是"跑一次、
   返回一块内容"——别拿它当 `setInterval` 使。
3. **没有任何东西保证"一秒就是一次"。** 那一拍是 `sleep(1s)` 之后才开始算的，机器忙的时候会漂，
   所以**时间要以宿主给的为准**，别在插件里自己攒计数。⚠️ 宿主给的时间有**两个**、用途不同：`nota.document.stats().clock_ms` 是**单调钟**（从启动算起，算"过了多久"用它，不受改系统时间影响），`nota.time.now()` 是**墙钟**（2026-09-27 加，回答"现在是哪一天/几点"，见 `docs/13` §16.1）。

⚠️ 今天只有一个用户：写作统计（`plugins/stats/`，`docs/13` §14.4）。跑法有两遍：**开窗**看画得对不对（`docs/06` §5.29），**无头状态测试**看时间走得对不对（`docs/06` §5.29b —— `GAP_MS` 15 秒与 `MIN_SPAN_MS` 10 秒那两条分支手点摆不出来，所以主力是那份无头测试）。⚠️ 上面第 2 条（"它不是定时器"）在这一轮又验了一次：用户要的「开始／暂停／终止」全部落成插件里的**状态**，宿主照旧每秒拉、拉的时候还是"跑一次、返回一块内容"——**没有一处变成"插件自己能醒来"**。

**⚠️ 只有"当前那一页"在被拉（2026-09-24）。** 右侧栏改成页签式之后
（一个插件独占一页，用户要求"两个拓展不能同时占用"，见 `docs/04` §右侧栏），
前端**只拉活动页**：没显示的那几页的 `render` 不会被调，`nota:plugin-panel`
的事件也只会让活动页重拉。所以：

- 好处是"用户不开的面板不花时间"（`render` 里那些子进程不会被空跑）；
- 代价是**切过去的一瞬间会现拉一次**（慢接口下会闪一下「正在读取…」）。
  这一次拉是**必须**的，不能依赖"事件刚到过、内容还新鲜"——插件得把
  **拉到的那一刻**算准（`render` 里不许缓存的另一条理由）。

**面板内容的大小上限**：宿主那一侧截大小（`ui.rs::面板文本上限` = **20000 字符**、
每块 200 项、嵌套 6 层）。⚠️ 这个数 **2026-09-24 从 4000 抬上来的**：
一条 `kind = "message"` 就是模型的一整段回答，4000 字在长回答上会被
**静默截断**（只留一个 `…`），用户会以为模型就写了这么多。超了是**截断不是报错**，
所以插件自己该截的还要自己截（AI 插件压到 15000，好让"后面还有内容"这句话
由插件说出来——见 `docs/13` §8.5）。

### 4.7 ⚠️ 插件代码跑在哪个线程上

**跑在后台阻塞线程上，不是主线程**，而且**不是插件自己的线程**：

| 事 | 事实 |
|---|---|
| 线程 | Tauri 的阻塞线程池（`tauri::async_runtime::spawn_blocking`） |
| 为什么 | 同步 Tauri 命令跑在主线程上；插件的 Lua 会起 `git` 子进程、发 HTTP，跑主线程上就是**冻界面**——窗口不重绘、按钮不响应，表现就是界面失去响应 |
| 靠什么搬得动 | mlua 的 `send` feature（§3） |
| 锁的语义 | ⚠️ **搬出去没改变锁**：仍旧是"跑这个插件的代码时一直握着 `plugins` 锁"，所以 `docs/03` 的锁序不变量照旧 |
| 一次调用多久 | **没有超时看门狗**（§6）。Lua 死循环会永久挂住那条 IPC，表现是按钮一直转，而且没有取消入口 |

⚠️ **推论：多个插件的命令是排着队跑的。** 一个插件的 `render` 卡住
（比如 git 在一个巨大的仓库上），别的插件的命令都得等——**这不是 bug，
是"一个 `plugins` 锁"的直接后果**，但它决定了"面板里不做重活"这条经验。

⚠️ 另一条推论：`on_load` 是**同步**跑的（加载时，串行），所以里面**不能发 HTTP**。
要联网就在命令或 `render` 里做，那里才在阻塞线程池上。

### 4.7a ⚠️ "面板里不做重活"这条经验，2026-09-26 落成了一条机制

§4.7 那条"多个插件的命令排着队跑"**不是抽象的**：`plugins/slidev` 的面板原先在
`render` 里**同步探一次**（那条探测要跑 `npx --version`：缓存命中 1.3 秒、没命中 0.26 秒、
挂住则 20 秒），于是**第一次打开那个页签什么都画不出来**——没有转圈、没有一句"正在检查"，
而且那段时间里**别的插件的命令一起排队**（`docs/07` BUG-36）。

**修法的形状值得记住：插件自己解决不了这件事。**
考虑过"面板分两趟画、探完由插件喊一声 `nota.ui.refresh`"，**做不到**——
**Lua 沙箱里既没有 timer，插件也收不到宿主事件**（只能 `nota.event` 往**前端**发），
所以第二趟**没人能画**。于是**探测搬回宿主**，多了一份托管状态：

| 事 | 在哪 |
|---|---|
| 结论的缓存 | `ProbeCache`（**第三个不进 `AppState` 的托管状态**，前两个是 `DevServerState` / `ReviewState`，见 `docs/01`） |
| `probe{}` 不等 | 有结论就回；没有就回一张 `state = "checking"` 并**在后台开一条** |
| `probe{force=true}` 才等 | "用户刚点了一下"的场合（`start`、「重新检测」）要的是**此刻**的结论 |
| 探完怎么叫醒界面 | 宿主后台线程发 `EVENT_PANEL_DIRTY`（`nota:plugin-panel`，载荷 `{plugin, id}`；`id` 为 null ＝"这个插件的每块面板都脏了"）→ 前端重拉那一页 |

⚠️ **这份缓存的细节（`Slot` / `Peek` / 为什么不设过期时间 / 为什么必须是另一把锁）
在 `docs/02` 的 `lua/api/devserver.rs` 那一节**；四档 `state` 的语义在 `docs/13` §13.3a。
⚠️ 一句话版本：**面板的 `render` 里只许问"现在知道什么"，不许做"现在去查一下"** ——
真要去查，就交给宿主开一条，让界面先画出来。

### 4.8 插件语言：清单声明 ＋ **加载时**协商（2026-09-25）

插件要支持多语言，**作者侧只写两样**：清单里的 `langs` 一行、以及 `lang/<tag>.toml`
一组文案表。运行时的规矩是这几条（口径的完整版在 `docs/11` §2.4，API 在 `docs/13` §`nota.i18n`）：

| 事 | 事实 | 为什么是这个形状 |
|---|---|---|
| **协商发生在加载那一刻** | `i18n::装` 在 `on_load` **之前**跑完 | 于是**换语言要重启**才生效——这是本设计最容易被当成 bug 的一条，写在这里当事实 |
| **`langs` 必须含 `en`** | 缺了**直接判这份清单不合法**（`plugin/manifest.rs::from_meta`，⚠️ **目前没有用例钉着这条**） | `en` 是没命中时的兜底：用户语言不在清单里就用英语，而且要在界面上**说明**（`ok = false` → 「此插件不支持您的语言」，落在插件栏与面板上） |
| **`ok` 只看清单，不看文件** | 声明了 `zh-CN` 却没放 `lang/zh-CN.toml` → 照样 `ok = true`，只是**每一条都退回原文** | 「支持这门语言」是**作者的声明**；文件缺失是打包问题，不该被说成"不支持你的语言"（不把话说过头） |
| **缺键给 `nil`** | `nota.i18n.text(key)` 取不到 → `nil`，标准写法 `nota.i18n.text(s) or s` | 键就是**作者写下的那句原文**，所以"没翻译"退化成的样子是**看见原文**，不报错、不缺字 |
| **不要能力** | `nota.i18n` **不在任何能力名下** | 路径由宿主拿**插件自己的目录**拼，插件只交键——它拿不到别人的文件，也没有额外的攻击面可给 |
| **保留键 `name`** | 覆盖清单里的 `name`，**不覆盖 `id`** | 插件名要能被翻译，但 `id` 是身份（签名、信任表、设置段都按它索引），翻译它等于换一个插件 |
| **保留键 `description`**（2026-09-27 加） | 覆盖清单里的 `description`，同样**不覆盖 `id`** | 理由与 `name` 一模一样——插件列表里那一行小字也要能翻译。⚠️ **主语言是英语**（用户 2026-09-27 定：「英文才是主语言，中文才是翻译包」）：清单里 `name` / `description` 写英语、中文进 `lang/zh-CN.toml`，**英语表通常不必写这两条**（口径在 `docs/11` §2.4 ②，API 在 `docs/13` §12.4） |

⚠️ **不写 `langs` 就不协商**：插件栏里不会出现那句话，插件一律显示 `main.lua` 里的原文。
这是留给第三方插件的自由（它们按自己的意思来），**不是漏了**。

⚠️ **宿主自己那一半**（应用界面语言、系统语言探测、`zh_CN.UTF-8 → zh-CN` 这类规范化）
在 `src-tauri/src/lang.rs`：**宿主与插件的协商都问它**，`lua/api/i18n.rs` 不自己写一套。
⚠️ 前端那一半走另一条路（`src/i18n/index.ts`：模块级 store ＋ `useSyncExternalStore`，
`t(原文, …参数)`，**不是 React context**），它的兜底（`兜底`）跟的是宿主的
**`应用兜底`**，**两边同值**（今天是 `en`）。
⚠️ **这一格 2026-09-26 一天里更正过两次**：原来写的是「与宿主 `lang::兜底 = "en"`
**故意不同**」，那句当天作废；随后写成「`应用兜底` = `zh-CN`」，那句在**同一天下午**
也过期了。经过是：宿主原来只有一个 `兜底 = "en"`，应用与插件共用，于是「跟系统走」
在认不出系统语言时会把**应用自己**落到英语，界面中英混杂（用户当天报的）——所以拆成
两个：**`插件兜底` = `en`**（对插件作者的要求，也就是本节上面各条讲的）与
**`应用兜底`**（应用自己的落点）。拆开时英文表只覆盖插件那一面，`应用兜底` 只能先取
`zh-CN`；当天下午表铺到整个界面（`tools/i18n-check.sh` 732 / 732、0 欠账）之后，
它按 `lang.rs` 里写下的条件翻回了 **`en`**。
⚠️ **两个兜底同值不等于合并**：两个概念、两个常量，各改各的（理由与那两次改动的经过
在 `lang.rs` 那两条常量的文档注释里）。📌 2026-09-28 前端语言翻转（**英语成了原文**、
中文成了翻译包）之后，`应用兜底` **那层"覆盖齐没有"的条件不用再看了**——英语界面的
完整性由构造保证。
⚠️ **这一节上面各条讲的全是 `插件兜底`**，与 `应用兜底` 取什么值无关。

### 5.2 实测：这句话是错的

（`lua54, vendored, serialize, send`），写一个十行的探针程序，`Lua::new()` 之后
逐个 `type(_G[...])`。下面是原样输出：

| 全局名 | 实测 `type()` | 注释说它在吗 |
|---|---|---|
| `debug` | **`nil`** | 不在 ✅ 唯一说对的一个 |
| `io` | `table` | 错 ❌ |
| `io.open` / `io.lines` / `io.popen` | `function` | 错 ❌ |
| `os` | `table` | 错 ❌ |
| `os.execute` / `os.exit` / `os.getenv` / `os.remove` / `os.tmpname` | `function` | 错 ❌ |
| `package` | `table` | 错 ❌ |

**它能做出实际的动作**（同一探针里跑的）：

```
package.cpath => /usr/local/lib/lua/5.4/?.so;...
```

### 5.3 机制：为什么注释会写错

`Lua::new()` 的内部是 `new_with(StdLib::ALL_SAFE, LuaOptions::default())`
（mlua `src/state.rs` 里 `Lua::new()` → `new_with` 那一行，0.12.1 是 :340），而：

```rust
pub const IO: StdLib = StdLib(1 << 2);          // 第 2 位
pub const OS: StdLib = StdLib(1 << 3);          // 第 3 位
pub const PACKAGE: StdLib = StdLib(1 << 8);     // 第 8 位
pub const DEBUG: StdLib = StdLib(1 << 31);      // 第 31 位
pub const ALL_SAFE: StdLib = StdLib((1 << 30) - 1);   // = 第 0 到第 29 位
```

（mlua `src/stdlib.rs` 里那批 `pub const ALL_SAFE` / `IO` / `OS` / `PACKAGE` / `DEBUG`，0.12.1 在 :26-100。）

`ALL_SAFE` 的掩码是**第 0 到第 29 位**——`IO`、`OS`、`PACKAGE`、`COROUTINE`
**全都在里面**，唯一被排除的是第 31 位的 `DEBUG`。
所以"安全子集"实际排除的库**只有一个**：`debug`。

而且 mlua 对 `DEBUG` 不是静默移除，是**直接报错**
（mlua `src/state.rs` 的 `new_with` 里那道安全检查，错误原文是 ``SafetyError("The unsafe `debug` module can't be loaded using safe `new_with`")``，0.12.1 在 :364-369。）
这更说明这个掩码不是"逐个审查过哪些库危险"，而是**一个 C 模块开关**。

### 5.4 mlua 的 "safe" 到底指什么

探针里 `require` 一个不存在的模块，错误信息末尾一句是：

```
can't load C modules in safe mode
```

**mlua 的 safe 只指不能加载 C 模块**（`.so`）。
**纯 Lua 文件仍可读取，`io`/`os` 仍然存在。** 注释作者把"不能 dlopen C 模块"
理解（或表述）成了"没有文件系统和进程能力"——一个**很自然但偏差很大**的推论。

### 5.5 为什么这不是学术问题

⚠️ **`nota.fs` 那道围栏挡不住任何一个会写 `io.open` 的插件。**

`docs/13` 会把 `nota.fs` 的围栏写得很硬：只收相对路径、`..` 在碰文件系统之前就解析掉、
符号链接逃逸会拒、没打开工作区时**一律拒绝**、`resolve_in()` 有单元测试。
**这些全都对，而且全都只作用于"走 `nota.fs` 的调用"。**

实际情况是：

| 一个插件在清单里声明 | 它实际能做的事（今天） |
|---|---|
| `ui.notify`（只想要个通知） | ⚠️ **读** `/etc/passwd`、**删**用户主目录下的文件、**起**任意进程、**往任意地址**发网络请求（`os.execute("curl …")`）。清单里一个字没提文件、进程、网络 |

也就是说：**能力表今天管的是"宿主 API 的可见性"，不是"插件能力的上限"。**
`docs/11` §3.2 那张表每行的"授予它 = 信任插件做 X"**只在"插件不会绕过 `nota.*`"这个前提下成立**，
而这个前提今天不成立。

### 5.6 现状定性：做到了什么、没做到什么

📌 **本节写于缺陷未修时；2026-09-22 已修（BUG-10）**。下表的 ❌ 那一行现已 ✅，
但**修法与下方 §5.7 的推荐方案不完全一样**——见 §5.7 的补充说明。

| | 未修时 | 现在 |
|---|---|---|
| **插件之间**互相隔离 | ✅ 成立（一插件一 `Lua` 状态，§2） | ✅ |
| 插件**报错**不带走宿主 | ✅ 成立（chunk 用 `pcall` 包着跑，§7） | ✅ |
| **"插件能做的事 = 清单申请到的事，没有旁路"** | ❌ **不成立**，旁路就是 `os.execute` 这么宽的东西 | ✅ **成立**——`io`/`os`/`package`/`require`/`loadfile`/`dofile`/`debug` 全部为 `nil`，有 4 条用例钉着（`docs/06` §6.1 `lua::tests`） |
| 插件**撑爆内存**时宿主不倒 | ❌ 不成立（§6） | ❌ 仍不成立 |
| 插件**死循环**时宿主不倒 | ❌ 不成立（§6） | ❌ 仍不成立 |

**未修时的准确定位是**：Nota 的插件**是"用户信任的代码"，与 Folio 的 `.so` 插件
处在同一个信任级别**——区别只在**故障隔离更好**，**不是安全隔离更好**。
这个定位现在变了：**故障隔离与安全隔离都成立**，但**后两项（内存、死循环）仍不成立**，
所以"插件是受信任代码"这个结论**只对这两项成立**。

### 5.7 修法（本文件原只记录、不动源码；2026-09-22 已按下面的 A+ 落地）

| 方案 | 怎么做 | 代价 |
|---|---|---|
| **A. 把那几个库真从掩码里摘掉** | `Lua::new_with(StdLib::STRING \| StdLib::TABLE \| StdLib::MATH \| StdLib::COROUTINE, …)` —— 显式列白名单，不用 `ALL_SAFE` | ⚠️ **`require` 会一起没**（`require`/`package`/`loadlib` 都不在）。今天两个内置插件都是单文件，**所以今天没有代价**——但要提前知道这个取舍 |
| **B. 保留 `io`/`os`，改文档与能力表** | 承认"插件是受信任代码"，能力表只描述宿主 API 的可见性 | 诚实，但**放弃沙箱叙事** |
| **C. 换到独立进程 / WASM** | 副作用全部绕回宿主 | 工程量大，且与"Lua 直接调宿主 API"的简洁**直接冲突** |

#### ⚠️ **A 单独用是不够的——实测推翻了本节的推荐**

本文件原本推荐 A。落地时补测了一次，**发现 A 有漏**：

```text
只做 A（列白名单、不额外抹任何东西）之后：
  io / os / package / require / debug   → nil      ✅ A 挡住了
  loadfile / dofile / load              → ★ 还在   ⚠️ 没挡住
```

原因：**`loadfile`/`dofile` 属于 base 库，而 base 库 mlua 是*无条件加载*的**
（`print`/`pcall`/`setmetatable` 都在里面，没法通过 `StdLib` 关掉）。后果实测：

```text
loadfile("/etc/hostname")        → 错误信息里把文件内容漏了出来
                                   （syntax error 会引原文那一行）
loadfile("/tmp/mlua-evil.lua")   → ★ 加载成功并执行了磁盘上任意 .lua
```

所以 A **单独**用，插件仍然能读并执行磁盘上的任意 `.lua` 文件——比 `os.execute` 窄，
但仍是实实在在的旁路。**真正的修法是 A + 显式抹除**：

```rust
// src-tauri/src/lua/mod.rs
fn 插件标准库() -> mlua::StdLib { /* COROUTINE | TABLE | STRING | UTF8 | MATH */ }

const 必须为空的全局: [&str; 7] = [
    "io", "os", "package", "require",
    "dofile", "loadfile",   // ← base 库给的，白名单关不掉，必须显式置 nil
    "debug",
];
```

**⚠️ 这条补充是本文件最值得记的一句**：**不能认为"列了白名单就安全了"**——
库会**无条件**加载一些没有申请的东西，而 `StdLib` 那种按位掩码的接口**表达不了
"要 base 库但不要 `loadfile`"**。列完白名单之后必须**把结果再验一遍**，
这正是 `docs/06` §6.1 里 `沙箱里不该有的全局一个都不能有` 那条用例的由来。

### 5.9 2026-09-27：补回来的那个 `require`（插件多文件）

§5.7 那次修法把 `require` 和 `package` 一起置了 `nil`（`硬化的_lua()` 里那份
`必须为空的全局`），理由是**成对的**：`require` 单独的失败原因只有一个
（`can't load C modules`），真正的危险是它后面的 `package.path` 与 `loadlib`。
代价是**一个插件只能有一个 `.lua` 文件**：四个内置插件里三个长到 997~999 行，
顶着 `docs/08` 那条 1000 行的硬线，其中写作统计那个（当时还叫 `heartbeat`）一个字都加不进去了。

于是 `装require()`（`lua/mod.rs`）补回**一个函数**。它不是"把 §5.7 反悔掉"，
判据是那张表里逐条对上的：

| 与真 `require` 的差别 | 挡住的正是 §5 里的哪一条 |
|---|---|
| **只认 `.lua`**，`.so` 一律不认 | `package.loadlib` —— 加载 C 模块等于整个沙箱不存在 |
| **只在本插件目录内**（`fs::resolve_in`） | 任意文件读取与执行：绝对路径拒、`..` 算掉、软链逃逸拒 |
| **没有 `package.path`** | 搜索路径是死的（就 `<名>.lua` / `<名>/init.lua` 两种），插件改不了 |
| 循环 require **报错**而不是栈溢出 | 真 Lua 在这里会顺着栈撞死，报错只有 `stack overflow`，看不出是谁要谁 |

⚠️ 所以 §5.2 那件事仍然成立：**`package` / `io` / `os` / `debug` 一个都没回来**。
这条有专门的用例钉着（`补上_require_不等于把_package_装回来`）——把
`StdLib::PACKAGE` 整个开回去是最省事的写法，而那正是 BUG-10 本人。

⚠️ 缓存与"在途"标记存在 **registry**（`nota_require_cache` /
`nota_require_loading`），不在 globals：插件可以合法地把全局 `require` 甚至
`nota` 覆盖掉（§4.6 旁边那段讲的是同一件事），而缓存被插件改坏的症状是
"同一个模块被求值两次"——只在模块里存了状态时才露头。

⚠️ 一处**已知的刻意不做**：模块名不许非 ASCII。原因不是洁癖，是报错信息会跟着
花掉（`docs/11` §1.3.1）。

⚠️ **第一个真用户是同一天拆出来的 `plugins/stats/ticks.lua`**（写作统计的刻度与"数怎么写"）。
挑它当第一个不是因为急，是因为它是那份插件里**唯一不碰状态**的一截：模块加载顺序、跨文件
的 upvalue、"两个文件共享一份状态会不会串味"这些新问题，在纯函数上没有藏身处。它拆完
`main.lua` 从 1000 行降到 910 行（`docs/08` 那条硬线是 1000，900 是警告线）。

⚠️ 那个模块的译文那一侧**不能**在模块加载时绑：`nota` 要到 `on_load` 才到手。所以
`ticks.lua` 里 `T` 先是一个"原样返回"的桩，由 `bind_text(f)` 换掉——**这是多文件插件的
一条通用规律**（模块级的字符串不该等 `nota`，等方法参数进来再绑），别把它当成这一个插件

⚠️ **同一天它又拆了两次**（`ledger.lua` 170 行：`days.txt` 的文件格式那一半；

这正是拿"唯一不碰状态的那一截"当第一个用户换来的。

⚠️⚠️ **但踩到了另一个坑，和 `require` 本身无关**：`ticks.lua` 拆出来那天

新增的那条边（`chat` → `request`）与 `store` 那条同形：**被依赖的那一份不认识"对话"**
（`request` 收下的就是一张消息表，回来是一段回答）。

📌 **第二次拆比第一次便宜**，因为这四件事（`require` / `bind_text` / 补 `PAIRS` / 单向依赖）
第一次全趟过一遍了——**这一条是"第一个用户"策略第三次付利息**。
⚠️ 但也踩到一个**新的、只在这一批出现的**坑：`request.lua` 忘了 `return M`。
Lua 的 `require` 在模块块什么都不返回时会把 `package.loaded["request"]` 记成 **`true`**，
于是调用点上那句 `request.ask(...)` 报的是 `attempt to index a boolean value`，
**而报错的位置在 `chat.lua` 里**——看着像 `chat.lua` 出了问题。
📌 判据：**新拆出来的每一份 `.lua` 末尾都得有 `return M`**，漏了的症状是
"另一个文件里报了一个莫名其妙的类型错"。

⚠️ **写作统计的第五份：`plugins/stats/cards.lua`（2026-10-04）**——它又一次是
**第一个用户**：那份 `main.lua` 被"面板改成运动手表那套版式"顶到 **1055 行**（破了
1000 那条硬线），于是照老判据（拆**唯一不碰状态**的一截）把"② 小字数据概览 ＋
④ 记录卡"搬了出去，`main.lua` 回落到 **985** ＋ `cards.lua` 141。

📌 这一份带来一条**新的**做法（前面几份都没有）：那几个函数**要读 `main.lua` 的状态**
（本轮字数、时长、相位、长期那本账），而 `require` 是**单向**的——子模块反过来
`require("main")` 就是一个环。解法是**一张显式递进去的 `ctx` 表**：`main.lua` 每画
一次面板现搭一张（`card_ctx()`），字段全是**取值**，`cards.lua` 只读、**一个字段都不
往回写**。⚠️ 这一条是判据的边界，别把它读松了：**"只读"不是"没状态就能破例"**——
那张表要是被写，就成了"藏在参数里的状态"，以后谁改了谁根本查不出来。
📌 判断顺序：**先看这一截认不认识状态**——不认识（`ticks`、`ledger`）就直接搬；
认识但**只读**（`cards`）就递一张显式只读表；**读写都要**（`diff.lua` 的
`show_diff`）就把状态**跟着实现一起搬走**，由它自己开访问器。

⚠️ 另一件值得记的**好事**：这一次 `PAIRS` 是**在"拆"的那一步就补上的**
（`tools/doc-sync-check.sh` 里 `plugins/stats/cards.lua` 那一行），前两次那个坑
（漏登记）这一次没有重演。

⚠️ **写作统计的第六份：`plugins/stats/share.lua`（2026-10-04 稍晚）**——同一天
的第二刀。第一次拆（`cards.lua`）之后 `main.lua` 是 985，加"Δt 滑杆"这一格
又顶回 **1061**，于是照同一把尺子再挑一截："**这一屏上摆什么**"——按钮表
（`TOGGLE`／`STOP`／`SHARE_BUTTONS`）＋ 分享那两张卡的字段 ＋ 长期那块热力图，
一共 262 行，`main.lua` 落到 **899**。

📌 **这次是 `ctx` 那条做法的第二次应用，也把它的边界又钉紧了一格**：
`share.lua` 要读的东西比 `cards.lua` 多得多（相位、两本账、窗口秒数、累计时长、
分享范围……一共 24 个字段），而规矩一个字没松——`main.lua` 那侧有个
`share_ctx()` 现搭这张表，`share.lua` 只读。⚠️ 有一处**特意没搬**：算刻度的那几个
函数（`ticks.lua` 里的整点标尺）**不通过 `require` 拿**，而是当成一个函数字段
递进 `ctx` 里。理由就是 `require` 单向——`share.lua` 直接 `require("ticks")` 也能跑，
但那会让"谁依赖谁"这件事在文件头上看不出来；递给它，依赖关系就写在 `share_ctx()`
那一张表里了。
⚠️ 顺带一个**真踩到的**坑：`share.lua` 里那几个函数挪过去之后，`main.lua`
调用点上全都得加 `share.` 前缀，而**加载期的顺序**又出了问题——`local sx = share_ctx()`
原来写在"分享那一屏"的分支里，而它在文件里出现在第一处使用**之后**，症状是
`share.lua:157: attempt to index a nil value (local 'ctx')`。把那一行**提到分支上面**
就好了。📌 判据：**子模块的 `ctx` 要在第一次用到它之前搭好**，别顺手写在分支里。

### 5.10 2026-10-04：宿主第一次**替插件写**设置文件

§4.5 那份 `~/.config/nota/plugin-settings/<id>.toml` 一直只有**一个写者**——
插件自己调 `nota.settings.set`。写作统计的 Δt 滑杆要的却是"宿主的界面（「设置 →
拓展」那一页）写、插件读"，于是当天多了一个写者：宿主的 `nota_plugin_setting_set`
命令。

📌 两个写者共用**同一份进程内的表**（注册表 `插件 id → Arc<Mutex<存储>>`），所以
插件自己 `get` 到的就是用户刚在设置页拖出来的那个数——**没有"宿主先写、插件后读"
的时序坑**。⚠️ 锁的顺序：注册表那把是**外层**且**短命**的（拿完立刻放），别把它
套在文件 I/O 外面。
📌 宿主写完会发一条 `nota:plugin-panel`（`{ plugin, id: null }`），意思是"该重拉了"。
⚠️ 这条消息**只为让界面立刻刷新**，不是缓存失效机制——插件那一侧本来就该**每一枪
现读**（`docs/13` §14.4 的 Δt 那一行）。⚠️ 反过来说：**别因为有了这条消息就去
缓存**，那条消息只在"用户拖滑杆"时来，插件重启、文件被手改都不来。
📌 那一格在清单里怎么声明（`[[settings]]`，宿主画什么、值存哪儿、要动哪几处）写在
`docs/11` §2.5；两个写者之间那三条纪律（锁顺序 / "值没变就别落盘" / 键的校验是
唯一一道门）写在 `docs/13` §10.1。

## 6. ⚠️ 明确没实现的东西

这张表是"现状清单"，不是 TODO 列表——**每一条都是现在就能观察到的事实**。

| 项 | 现状 | 现在会怎样 |
|---|---|---|
| **插件与宿主同进程** | 事实。`LuaPlugin` 就是宿主进程里的一个结构体 | 插件里 `os.exit()`（**它在**，§5.2）→ **整个 Nota 退出**。插件触发一次 C 层崩溃 → 宿主一起没 |
| **没有内存上限** | 没有 | 一个 `while true do t[#t+1] = string.rep("x", 1e6) end` 能把进程 OOM 掉 |
| **没有 CPU 上限 / 没有超时看门狗** | 没有 | 一个死循环的命令回调**永久挂住**调它的那次 IPC。前端是 `invoke(...)` 等 Promise，表现是那个按钮一直转，**而且没有"取消"的入口** |
| **没有指令数钩子** | 没有。**唯一能实现这事的 `debug` 恰好是唯一被挡掉的库**（§5.3） | 想加"限制执行步数"这类保护，需要先把 `debug` 开回来（`new_with` 会直接拒——见 §5.3 那道安全检查），所以这条实现起来并不简单 |
| **没有权限提示** | 装插件不弹任何框 | 清单里的能力只在侧栏「插件」页列出来（`docs/11` §6.2），**需要用户自己查看**。⚠️ 叠加 §5，这个列表今天还会**低估**插件实际能做的事 |
| ~~**卸载不彻底**~~ ✅ **2026-09-25 已结清** | 停用（`set_enabled(false)`）现在**跑 `on_unload` 并把 Lua 状态整个丢掉**，启动时停用过的插件也不新建状态（`LuaPlugin::disabled`） | 代价换了个方向：**重新启用会重跑 `on_load`**，所以 `on_load` 必须幂等（`docs/11` §1.6.7） |
| **插件设置是明文的** | `~/.config/nota/plugin-settings/<id>.toml`，0600 | 见 §4.5。**这是决定，不是欠账**——不该把它"修"成加密 |
| ~~`nota.http` / `nota.settings` 是假表~~ | ✅ **2026-09-24 已成真** | 见 §4.4 的历史。现在只有"没有流量上限"这类**运行时**约束还留着：插件能一直发请求，宿主不计数也不拦 |

⚠️ **和 Folio 那两把锁的对比**：Folio 的 Lua 扩展沙箱有**内存**与**时间**两把锁，
Nota 这边**一把都没有**。这不是"还没来得及"，而是**当前设计没把沙箱当成边界**
（§5 那句话是同一件事的另一面）：既然不能保证插件只做清单里的事，
那么"限制它做多少"就还没有立足点。**先把 §5.7 定了，再谈这两把锁。**

## 7. 故障隔离：现在实际做到了什么

这些机制**是实际生效的**；§5 不意味着整个运行时不可信——
它们是"错误隔离"，不是"故障隔离"（§6）。区别很重要。

| 机制 | 在哪 | 效果 |
|---|---|---|
| 入口 chunk 用 `eval()` 跑，错误折成 `state = Failed(原因)` | `lua/mod.rs` 的 `run_entry()` | Lua 语法错 / `on_load` 抛错 → 这个插件标红，**宿主照常启动** |
| `load()` **不返回 `Err`** | `lua/mod.rs` 的 `LuaPlugin::load()` | 一个插件坏掉不该让整个启动流程挂掉。理由很实在（`src-tauri/src/plugin/mod.rs` 的「一个插件坏掉不能拖垮启动」那一节）：**让一个写错的 Lua 脚本变成"应用打不开"，用户连去禁用它的界面都进不去** |
| `on_unload` 的报错**只记不抛** | `lua/mod.rs` 的 `unload()` | 卸载流程不被一个插件的失败卡住 |
| 撞名插件走 `rejected()`，不另造状态 | `lua/mod.rs` 的 `rejected()` | 两种失败对界面来说长得一样（一行标红 + 一句原因） |
| 模块表存 **registry** 而不是 globals | `lua/mod.rs` 的 `run_entry()`/`unload()` 里那对 `nota_module`、`api/mod.rs` 里那对 `nota_commands` | ⚠️ 理由：**插件可以合法地把全局 `nota` 覆盖掉**，所以宿主自己的东西不能放在会被借走的名字下 |

### 7.1 ⚠️ 但"记下来了"≠"看得见"：插件日志默认不打（2026-09-25）

上表里两条写着"只记不抛"（`on_unload` 出错、`api/mod.rs` 的插件清单读不了），
`nota.log.*` 那一族也一直是往 stderr 写的——**这些从 2026-09-25 起统统归了
一道调试闸门**（`src-tauri/src/log.rs`，插件侧没有例外），**默认一行都不输出**，
要 `NOTA_DEBUG=1` 启动才有。

所以这个文件的读者要记牢一条：**"插件没报错"和"日志没开"从终端上看不出区别**。

- 插件自己那张 `nota.log.{info,warn,error}` 表**功能不变**（签名、渲染规则照旧，
  见 `docs/13` §2），变的只是**默认不落盘到任何地方**；
- 因此**插件不该拿它当用户提示**——它对用户从来不可见（只到 stderr），
  现在默认对开发者也不可见。要对用户说话走 `nota.ui.notify`；
- 用户能看见的那几条路一条都没动：插件加载失败仍是侧栏「插件」页那行标红
  （`plugin/types.rs::PluginInfo.state`），命令失败仍是 `NotaError` 的人话。

⚠️ 为什么要把"错误隔离"和"日志可见性"分开说：这两个是**不同的问题**——
前者保证"一个插件坏掉不拖垮宿主"（本节的机制），后者决定"坏掉的事有没有人知道"。
闸门动的是后者，**没有削弱前者**。

⚠️ **"错误隔离"的边界在哪**：`pcall` 抓得住 Lua 的 `error()`、
抓得住 `attempt to index a nil value`，**抓不住** `os.exit()`、进程被 OOM 杀掉、
C 层 abort。§6 那几条之所以是"没实现"而不是"不会发生"，就是因为这个边界。
