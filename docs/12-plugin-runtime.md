## 1. 为什么是 Lua

### 1.1 一句话

因为**插件的作者不是 Rust 开发者**。一个 Markdown 编辑器的插件生态，
主力是"想把某个自己天天干的小活自动化"的人——他愿意写二十行脚本，
不会愿意装一套 Rust 工具链、学一遍生命周期、为改一个字符串重编 30 秒。

### 1.2 与其它方案的对比

| 方案 | 好在哪 | 死在什么上 |
|---|---|---|
| **Lua**（选它） | 解释器小、嵌入成本低（mlua 一行 `Lua::new()`）、**纯文本单文件、改完存盘就是新版本**、语法足够写"解析 git 输出"这种活 | 动态类型：插件作者写错字段名要到运行期才知道；⚠️ 另外 mlua 的"安全子集"**自带完整文件系统与进程能力**（§5）——**本仓已自己收紧，见 `docs/07` BUG-10** |
| 进程内 C ABI（`.so`） | 最快、无障碍调宿主 | 要编译工具链 + 稳定的 C ABI + **段错误就是宿主的段错误**。这是 Folio 走的路（`AGENTS.md` §1 那张对比表），它要的是性能与原生 GTK 控件的接入；Nota 这边没有这个诉求 |
| WASM | 隔离最干净（内存沙箱 + 指令计数都是白送的） | 要引入一整个运行时，宿主 API 得先序列化过界、再在 wasm 侧重新做一套绑定；**"插件就是一串字符串"这个最简单的卖点没了** |
| 嵌入式 JS（QuickJS） | 心智与前端一致 | 宿主里多一个 JS 引擎，而**前端 WebView 里本来就有一个 JS**——两边的 `nota` 不是同一个对象，插件作者一定会混。文档得花半页解释"你写的 JS 跑在 Rust 里，不是那个 JS" |
| 纯声明式（只留 TOML） | 没有代码就没有沙箱问题 | 表达力不够。`plugins/git/main.lua` 要按 `-z` 分割 NUL、按状态字母归类、拼命令行——**这是逻辑，不是配置** |

⚠️ **另有一条不好写进表里的理由**：工作区里的 Folio 也用了 Lua
（见 `docs/01-architecture.md` 的家族说明）。**同一位作者的两个项目用同一套插件语言**，
意味着插件作者的心智、踩过的坑、写文档的口径都能复用。这条对"选什么语言"的影响
通常比技术指标大。

### 1.3 代价（选之前要知道的）

| 代价 | 具体表现 |
|---|---|
| **动态类型** | 能力名拼错、命令名拼错、函数签名记错，**都在运行期才知道**。宿主能做的只有把错误信息写清楚（`docs/11` §2.2、§6.5） |
| **一门新语言要学** | 对只写前端/后端的用户，Lua 的表/元表/`pcall` 是新东西。所以 `plugins/` 里那两个插件**同时是样例**——照抄比读文档快 |
| **宿主 API 要手工维护两层判据** | 每加一个 `nota.*` 成员，就要在"表装不装"和"成员装不装"两处各判一次能力。⚠️ **BUG-8 就是这个手工维护漏了一格**（§4.3） |
| **同进程**（§5、§6） | 故障隔离做到了；安全隔离**曾经没做到，2026-09-22 起做到了**（BUG-10）。⚠️ 但**内存与死循环仍不隔离** |

## 2. 一个插件一个 `Lua` 状态

### 2.1 事实

```
LuaPlugin { manifest, lua: Lua, state, has_unload }     // src-tauri/src/lua/mod.rs 的 `struct LuaPlugin`
```

每个插件**自己一个** `Lua`——`LuaPlugin::load()` 里调 `硬化的_lua()`（**曾经是
`Lua::new()`，见 §5 与 `docs/07` BUG-10**）。不是共享池、不是按需创建：
`rejected()`（撞名被拒的插件）甚至都要先建一个空状态，
代价换的是"两种失败对界面来说长得一样"。

### 2.2 ⚠️ 这是与 Folio **有意相反**的设计

| | Folio | Nota |
|---|---|---|
| 插件形态 | 进程内 C ABI（`.so`） | Lua 状态 |
| 隔离粒度 | **没有隔离**（无沙箱） | **Lua 状态** |
| 宿主 API 可见性 | 插件能链到的符号都能调 | 按能力**装配**（§4） |
| 插件崩了 | **宿主一起死** | 这个插件判失败，宿主继续跑 |

（上表前两行的对比照 `AGENTS.md` §1「与 Folio 的关键差别」。
那条表还提醒了一句：**别照搬那边的结论**——这里正是它指的地方。）

`src-tauri/src/lua/mod.rs` 的模块注释把这条对比写进了源码：

> 整个 chunk 用 `pcall` 包着跑——**插件炸了不能带走宿主**
> （这条与 Folio 的 C 插件相反：那边同进程无沙箱，插件的段错误就是宿主的段错误）。

### 2.3 收益（照 `lua/mod.rs` 模块注释里"一插件一状态"那三条）

1. **隔离**：一个插件把脚本写崩（栈溢出、抛错），影响不到别的插件，也影响不到宿主。
   ⚠️ 注意原文里"栈溢出"这个词——实际上 Lua 层的栈溢出是被 `pcall` 变成错误的，
   而 **C 栈溢出 / OOM / `os.exit()` 不在隔离范围内**（§5）。
2. **能力放行是天然的**：`nota.document` 这张表**只在插件申请了
   `document.read`/`document.write` 时才存在**——不是"存在但调用时报错"。没申请
   `process.git` 的插件，`nota.git` 那格就是 `nil`，"写不出来也绕不过去"。
3. **卸载 = 丢掉这个 `Lua`**：不用做引用计数、不用管谁还拿着回调。

第 2 条是这套设计里最漂亮的一处，**但它的前提在 §5 被推翻了**——
按能力装配管的是"宿主递给插件什么"，管不了"插件自己能拿什么"。
模块注释里那句"脚本能做的事 = 清单申请到的事，没有旁路"**曾经是假的**
（`os.execute` 就是旁路）——**2026-09-22 收紧标准库之后它才成立**（§5、BUG-10）。

### 2.4 代价

| 代价 | 说明 |
|---|---|
| **内存**：每插件一份解释器 + 一份标准库 | 内置插件只有两个，感知不到；⚠️ **没有上限、没有池化、没有共享只读段**。装几十个插件的用户会看到内存随插件数线性上涨 |
| **没有跨插件的共享内存** | 插件之间的协作只能过宿主（而宿主那半还没实现，见 `docs/11` §7） |
| **重复建表** | 每个插件的 `nota.*` 都重新构造一遍（`api::build`）。命令表、面板表、菜单表也都是每插件一份 |
| **编译好的 chunk 不能共享** | 每个状态都从头 `load` 一次入口脚本 |

⚠️ **代价的量级判断**：两份内置插件一共不到 350 行 Lua。这个取舍今天是明显划算的
（用一点内存换掉整个 C ABI 稳定性问题）；**它划不划算取决于插件数量**，
所以这是将来该回看的一条，不是永久结论。

## 3. 为什么必须开 mlua 的 `send`

```toml
# send：Lua 状态要放进 Tauri 的 managed state（跨线程），不加这个 feature
#       编译期就会因为 Lua 不是 Send 而卡住。
mlua = { version = "0.12", features = ["lua54", "vendored", "serialize", "send"] }
```

（`src-tauri/Cargo.toml` 的 `mlua = …` 那一行及其上方注释。）

### 3.1 精确的因果链

1. `LuaPlugin` 存在 `PluginHost` 里；
2. `PluginHost` 进 Tauri 的 managed state（`lib.rs` 里 `app.manage(...)`）；
3. Tauri 的 managed state 要求 `Send + Sync`；
4. **不开 `send`，`mlua::Lua` 不是 `Send`** → 第 2 步编译不过。

mlua 对这个 feature 的定义（`README.md`）：

> `send`: make `mlua::Lua: Send + Sync`
> (adds `Send` requirement to `mlua::Function` and `Send + Sync` to `mlua::UserData`)

⚠️ 注意后半句：它**顺带把要求加到了 `Lua` 之外的类型上**。所以哪天要给插件做
`UserData`（把 Rust 结构体暴露成 Lua 对象），那个结构体也得是 `Send + Sync`。
这是开了这个 feature 之后才生效的约束，加新类型时会被编译器提醒——是好事。

### 3.2 ⚠️ `send` 不是"线程安全"，只是"能跨线程移动"

`send` 是**类型层面的开关**，不是运行时锁。它让 `Lua` 可以放进 `Mutex` 里被多个线程
持有，**不等于**你可以并发地进同一个 `Lua`。

真正管住并发的是这三样，都是本仓自己写的：

| 手段 | 在哪 |
|---|---|
| `Arc<Mutex<DocumentStore>>` / `Arc<Mutex<Settings>>` / `Arc<Mutex<Option<PathBuf>>>` | `HostContext`（`lua/mod.rs` 的 `struct HostContext`），`HostContext` 本身 `#[derive(Clone)]`——每个闭包克隆一份，**里面共享的是同一批 `Arc`** |
| **锁序不变量**：`plugins → documents → settings`，只能从左往右 | `lua/mod.rs` 的 `struct HostContext` 文档注释与 `state.rs` 的文件头各写了一遍 |
| 命令调用走 `PluginHost` 的锁 | `plugin/mod.rs` |

⚠️ **锁序那一条值得单独记住**：违反它的后果是**死锁，而且是最难查的那种**——
平时不触发，只在插件的 Lua 回调（持着 `plugins`，要读 `documents`）和存盘流程
（持着 `documents`，要读 `settings`）**碰巧同时跑**时才卡住。
它不会报错，只会让界面停在那儿。

### 3.3 `vendored` 是另一个"没得选"

```toml
# vendored：把 Lua 5.4 源码一起编进来，不依赖系统 liblua（容器里也没有）。
```

（`Cargo.toml` 的 `vendored` 那行注释。）这条不需要解释得太细：**容器里没有系统 liblua**，
所以不 vendored 就是构建直接失败。⚠️ 顺带的好处是**版本锁死**——
`lua54` 指的是 Lua 5.4 的语义，宿主带的是自己编的那一份，
不会因为用户机器上的 liblua 是 5.3 而行为不同。

## 4. 沙箱的墙画在哪：**按能力装配**，不是黑名单

### 4.1 口径

`lua/api/mod.rs` 的模块注释（「一条硬规矩：**按能力装表，不装空壳**」那段）把口径写得很清楚，两层：

1. **按能力装表，不装空壳。** 没申请 `document.read`，`nota.document` 就是 `nil`——
   不是"存在但调用时报错"。理由：前者让插件作者**在开发期**就发现问题，后者写完才炸；
   也让"权限"变成一道**结构上的墙**，而不是一句运行时的客气话。
2. **每个能力对应一张表的一部分**，表里的成员各自再判一次。

一个推论值得单独说：**没有"删全局变量"这道工序**。
宿主不往 Lua 里塞危险东西、也就不需要去删什么——
黑名单的毛病是"默认开、漏一个就是一个洞"，而且事后审计得逐行读代码才知道谁有什么权限；
白名单是"默认关、显式开"，权限清单就是清单文件本身。

⚠️ **但这个口径有个隐含前提：墙外的世界是空的。** 如果 Lua 状态里已经有一整套
文件系统与进程能力，那么"删全局变量"这道工序不是"不必要"，而是**"还没做"**——
而 `Lua::new()` 给的正是那样一个世界。§5 是证据，**本仓后来就把这道工序补上了**
（`硬化的_lua()` 里那个 `必须为空的全局` 循环）。

### 4.2 两层判据

| 层 | 判据写在哪 | 内容 |
|---|---|---|
| **表装不装** | `lua/api/mod.rs` 的 `fn build()` 里那一串 `if manifest.has(…)` | `document`（`document.read` 或 `document.write`）、`fs`（`fs.read` 或 `fs.write`）、`git`（`process.git`）、`ui`（`ui.notify` 或 `ui.panel` 或 `ui.menu`——三条都在，见 §4.3）、`http` / `settings`（各自的单项能力） |
| **表里成员装不装** | `document.rs` / `fs.rs` / `ui.rs` 各自开头 | 例如 `ui.rs` 的 `build()` 里三处判据各守一个成员：`UiNotify` → `notify`、`UiPanel` → `register_panel`、`UiMenu` → `register_menu` |

**两层是相乘的**：只申请 `ui.panel` 的插件，`nota.ui` 表存在、`register_panel` 存在，
但 `register_menu` 是 `nil`。

⚠️ **所以"表装不装"这层的判据必须把该表下面的**每一条**能力都列上。**
这是本节唯一一处**手工维护**的地方，也是唯一一处漏过东西的地方（§4.3）。

### 4.3 ⚠️ BUG-8：第一层曾经漏了一格（已修）

第一层那行条件**曾经**是：

```rust
if manifest.has(Capability::UiNotify) || manifest.has(Capability::UiPanel) {
    set(nota.set("ui", ui::build(lua, manifest, ctx)?), lua)?;
}
```

**漏了 `Capability::UiMenu`**，而 `ui.rs` 里 `register_menu` 那一格是**按 `UiMenu` 装的**。
于是两层判据对不上：

- 插件**只**申请 `ui.menu` → `nota.ui` 是 **`nil`** →
  `nota.ui.register_menu{...}` 报 `attempt to index a nil value (global 'nota.ui')`。
  **`ui.menu` 这条能力形同虚设。**
- 申请了 `ui.menu` **加** `ui.notify` 或 `ui.panel` → 一切正常。

两个内置插件都申请了 `ui.panel`（`plugins/git/plugin.toml`、`plugins/ai/plugin.toml`），
所以一直没暴露。

#### 修法是"两层同源"，不是补一个 `||`

**✅ 已在 2026-09-22 修掉**。做法不是随手补一个条件，而是让**第一层的判据由一张能力
清单产生**，并且让那张清单与 `ui.rs` 里的判据**数量挂钩**——这样下一格不会再漏：

```rust
/// 装 `nota.ui` 这张表需要哪些能力。
/// ⚠️ `ui.rs` 里每多一个 `manifest.has(Capability::Ui…)`，这里就要多一项。
/// 两处是**相乘**的关系：里面那个判据决定"表里有没有这个函数"，
/// 外面这个决定"表本身在不在"。漏一个就是 BUG-8。
const UI能力: [Capability; 3] = [Capability::UiNotify, Capability::UiPanel, Capability::UiMenu];

/// `nota.ui` 这张表装不装。**纯函数**，单独剥出来是为了能被用例钉住。
fn 装_ui吗(manifest: &Manifest) -> bool { UI能力.iter().any(|c| manifest.has(*c)) }
```

（`api/mod.rs` 的 `const UI能力` 与 `fn 装_ui吗`。剥成纯函数的原因写在注释里：`build()` 要真的 `AppHandle`、
构造不出来，而这条判断是纯的，正是最该被用例钉住的那一条。）

**同批加的 4 条回归用例都在 `lua::api::tests`：**

| 用例 | 钉住什么 |
|---|---|
| `每一条_ui_能力都能单独装出_nota_ui` | 遍历 `UI能力` 逐项造清单 —— **BUG-8 的回归** |
| `没申请_ui_能力就不装_nota_ui` | 反向：一个 `ui.*` 都没申请就不该有表（按能力装表、不装空壳） |
| `ui_能力清单要和_ui_rs_对得上` | `UI能力` 的项数 == `ui.rs` 里 `manifest.has(Capability::Ui` 的出现次数。⚠️ **Rust 没有反射，这条推不出来，所以退一步钉"数量"**——谁往 `ui.rs` 加第四个 `ui.*` 判据，它就会红 |
| `能力的_serde_名字与_parse_说同一套话` | `#[serde(rename)]` 与 `Capability::parse()` 的两套名字必须同口径 |

**测试数因此从 32 条变成 36 条**（计数只在 `docs/06` 记）。
`docs/07` 的 **BUG-8** 登记的就是这条缺陷，编号永久保留、状态列改成已修。

📌 这条顺带留了个**方法论教训**（`docs/07` §4 的漂移登记表里记的是同一次事故）：
核对时只 `grep -n` 到下一行的 `set(...)`、**没看上一行的 `if`**，就会得出
"无条件调用、文档在编"这种**完全相反**的结论。判断"这里没有条件"必须看上下文几行。

### 4.4 ⚠️ 两张假表的历史（已于 2026-09-24 结清）

`nota.http` / `nota.settings` 在 2026-09-24 之前是**故意装出来的假表**：
用 `__index` 元表兜住任意方法名，**任何一次调用都抛**一句带文档条目号的错误。

**为什么当时给假表而不是不给**：给的是**线索不是哑弹**。有了它，插件作者写
`nota.http.get(...)` 立刻拿到「网络请求尚未实现（见 docs/07 第 12 项）」；
没有它，拿到的是 `attempt to index a nil value`——后者会让人**误以为是自己的能力没申请对**，
白查半天。

**这个做法是对的，但它只该用来买时间。** 空壳终究是空壳：AI 插件因此只能预览、
存不住密钥，"联网"那半等于没有。**本轮（`docs/07` 第 12、13 项）两样都真做出来了**
（`lua/api/http.rs`、`lua/api/settings.rs`），`not_implemented()` 与它那套元表
已经删掉——`api/mod.rs` 里只剩一段注释记着这件事，因为**"当时为什么这么做"值得留下，
"这么做"不值得**。

### 4.5 插件设置为什么不加密

用户的密钥就存在 `~/.config/nota/plugin-settings/<id>.toml`，**没有加密**。
这不是偷懒，也不打算以后补上——理由如下，**改这个决定之前先读完**。

**它能挡住谁**：同机器上的其他用户（文件 0600、目录 0700），
以及"设置被顺手贴进 issue"（面板上的 `secret = true` 让输入框遮屏）。
这两件是真实的、经常发生的。

**它挡不住谁**：能读你这个账号文件的任何人或程序。**而加密也挡不住**——
插件运行时要拿明文去发请求，密钥就必须能在**进程内存里**被解出来，
而解密用的那把钥匙只能存在同一台机器上的同一个账号能读到的地方。
把锁和钥匙放进同一个抽屉，挡住的还是"打不开抽屉的人"。
**加密在这里买到的是"看起来更安全"，代价是一个能被自己搞丢的密钥文件
（丢了就是所有插件设置全部读不出来）。**

**真正该做的两件事，是另外两件**：

| 事 | 状态 |
|---|---|
| **限制谁能读** | ✅ 文件 0600、目录 0700。这是唯一一条真正有效、且不依赖用户操作的防线 |
| **让密钥别到处跑** | ✅ `settings.own` 只能读**自己那一个文件**（`build()` 拿到的是本插件的 id），所以 AI 插件拿不到 git 插件的设置 |
| 上系统密钥环（libsecret / Keychain） | ❌ **不做**，理由见下 |

**为什么不上系统密钥环**：那会把"插件设置"从一个纯文本文件变成一个**依赖桌面会话**
的东西——无头环境、SSH、容器里全都拿不到；解密失败时的症状是"设置莫名其妙没了"。
它还要求每个用户装并解锁一个密钥环服务。**对"存一个 OpenAI key"这件事，代价远大于收益。**
哪天插件要存的是能直接动钱的凭据，这条要重新判一次——那时也应该是**插件自己**
去要密钥环，而不是把整张 `nota.settings` 变成密钥环。

⚠️ **所以别在文档和界面上说它"安全"。** 该说的是原话：**明文、0600、
只给这个插件看**。用户有权知道这一点再决定填不填。

### 4.6 面板内容：**一次拉**，不是一个频道

面板这条路被拆成了**两件不同的事**，混起来就是 BUG-13：

| | 声明 | 内容 |
|---|---|---|
| 是什么 | "我有这么一块面板，叫 Git" | "它此刻长这样" |
| 谁写的 | `nota.ui.register_panel` / `register_menu` | `render` 函数的返回值 |
| 什么时候发生 | `on_load` 里**一次** | **每次有人要就现跑一遍** |
| 怎么到界面 | 前端挂载后 `nota_plugin_panels` **拉** | `nota_plugin_panel_content(plugin, id)` **拉** |

两条命令**都是 `async` + `spawn_blocking`**（`commands/plugin.rs`）：`render` 里
常常要起 `git status` 子进程、发 HTTP 请求，跑在主线程上就是冻界面。

**那 `nota.ui.refresh("ai")` 是什么？** 它只做一件事：往界面喊一声
「我这边变了，去重拉一次」（前端收到 `nota:plugin-panel`，然后调上面那条
`panel_content`）。⚠️ **它是一条"失效通知"，不是内容的通道**——
谁都不该往这条事件里塞内容。判据很简单：**把这条事件整个丢掉，面板打开时
仍然显示正确的东西**（因为打开时本来就会拉一次）。丢掉它就显示不出来的设计，
说明内容被存了两份。

⚠️ **`nota.ui.refresh` 的代价是每次都要重跑一遍 `render`**，而 `render` 里通常是
一个子进程。所以别在循环里调它，也别指望它"顺便"更新别的东西。

### 4.7 ⚠️ 插件代码跑在哪个线程上

**跑在后台阻塞线程上，不是主线程**，而且**不是插件自己的线程**：

| 事 | 事实 |
|---|---|
| 线程 | Tauri 的阻塞线程池（`tauri::async_runtime::spawn_blocking`） |
| 为什么 | 同步 Tauri 命令跑在主线程上；插件的 Lua 会起 `git` 子进程、发 HTTP，跑主线程上就是**冻界面**——窗口不重绘、按钮不响应，看着就是"卡死了" |
| 靠什么搬得动 | mlua 的 `send` feature（§3） |
| 锁的语义 | ⚠️ **搬出去没改变锁**：仍旧是"跑这个插件的代码时一直握着 `plugins` 锁"，所以 `docs/03` 的锁序不变量照旧 |
| 一次调用多久 | **没有超时看门狗**（§6）。Lua 死循环会永久挂住那条 IPC，表现是按钮一直转，而且没有取消入口 |

⚠️ **推论：多个插件的命令是排着队跑的。** 一个插件的 `render` 卡住
（比如 git 在一个巨大的仓库上），别的插件的命令都得等——**这不是 bug，
是"一个 `plugins` 锁"的直接后果**，但它决定了"面板里别做重活"这条经验。

⚠️ 另一条推论：`on_load` 是**同步**跑的（加载时，串行），所以里面**别发 HTTP**。
要联网就在命令或 `render` 里做，那里才在阻塞线程池上。

### 5.2 实测：这句话是错的

**怎么测的**：拿项目**正在用的同一个** mlua 0.12.1、**同一组 feature**
（`lua54, vendored, serialize, send`），写一个十行的探针程序，`Lua::new()` 之后
逐个 `type(_G[...])`。下面是原样输出：

| 全局名 | 实测 `type()` | 注释说它在吗 |
|---|---|---|
| `debug` | **`nil`** | 不在 ✅ 唯一说对的一个 |
| `io` | `table` | 错 ❌ |
| `io.open` / `io.lines` / `io.popen` | `function` | 错 ❌ |
| `os` | `table` | 错 ❌ |
| `os.execute` / `os.exit` / `os.getenv` / `os.remove` / `os.tmpname` | `function` | 错 ❌ |
| `package` | `table` | 错 ❌ |
| `require` | `function` | 错 ❌ |
| `dofile` / `loadfile` / `load` | `function` | 错 ❌ |
| `coroutine` / `collectgarbage` | `table` / `function` | （注释未提，但存在） |

**它能干出真事**（同一探针里跑的）：

```
os.execute 起进程 => true / code=0          ← os.execute("touch /tmp/mlua-pwned") 真的建了文件
io.open 读 /etc/hostname => 成功：toolbx     ← 工作区围栏之外的文件，读到了
package.cpath => /usr/local/lib/lua/5.4/?.so;...
```

### 5.3 机制：为什么注释会写错

`Lua::new()` 的内部是 `new_with(StdLib::ALL_SAFE, LuaOptions::default())`
（mlua `src/state.rs` 里 `Lua::new()` → `new_with` 那一行，0.12.1 是 :340），而：

```rust
pub const IO: StdLib = StdLib(1 << 2);          // 第 2 位
pub const OS: StdLib = StdLib(1 << 3);          // 第 3 位
pub const PACKAGE: StdLib = StdLib(1 << 8);     // 第 8 位
pub const DEBUG: StdLib = StdLib(1 << 31);      // 第 31 位
pub const ALL_SAFE: StdLib = StdLib((1 << 30) - 1);   // = 第 0 到第 29 位
```

（mlua `src/stdlib.rs` 里那批 `pub const ALL_SAFE` / `IO` / `OS` / `PACKAGE` / `DEBUG`，0.12.1 在 :26-100。）

`ALL_SAFE` 的掩码是**第 0 到第 29 位**——`IO`、`OS`、`PACKAGE`、`COROUTINE`
**全都在里面**，唯一被排除的是第 31 位的 `DEBUG`。
所以"安全子集"实际排除的库**只有一个**：`debug`。

而且 mlua 对 `DEBUG` 不是"悄悄剥掉"，是**直接报错**
（mlua `src/state.rs` 的 `new_with` 里那道安全检查，错误原文是 ``SafetyError("The unsafe `debug` module can't be loaded using safe `new_with`")``，0.12.1 在 :364-369。）
这更说明这个掩码不是"逐个审查过哪些库危险"，而是**一个 C 模块开关**。

### 5.4 mlua 的 "safe" 到底指什么

探针里 `require` 一个不存在的模块，错误信息末尾一句是：

```
can't load C modules in safe mode
```

**mlua 的 safe = 不能加载 C 模块**（`.so`），仅此而已。
**纯 Lua 文件照读，`io`/`os` 照给。** 注释作者把"不能 dlopen C 模块"
理解（或表述）成了"没有文件系统和进程能力"——一个**很自然但错得很远**的推论。

### 5.5 为什么这不是学术问题

⚠️ **`nota.fs` 那道围栏挡不住任何一个会写 `io.open` 的插件。**

`docs/13` 会把 `nota.fs` 的围栏写得很硬：只收相对路径、`..` 在碰文件系统之前就解析掉、
符号链接逃逸会拒、没打开工作区时**一律拒绝**、`resolve_in()` 有单元测试。
**这些全都对，而且全都只作用于"走 `nota.fs` 的调用"。**

实际情况是：

| 一个插件在清单里声明 | 它实际能做的事（今天） |
|---|---|
| `ui.notify`（只想要个通知） | ⚠️ **读** `/etc/passwd`、**删**用户主目录下的文件、**起**任意进程、**往任意地址**发网络请求（`os.execute("curl …")`）。清单里一个字没提文件、进程、网络 |

也就是说：**能力表今天管的是"宿主递出去的那只手"，不是"插件能力的天花板"。**
`docs/11` §3.2 那张表每行的"授予它 = 信任插件做 X"**只在"插件不会绕过 `nota.*`"这个前提下成立**，
而这个前提今天不成立。

### 5.6 现状定性：做到了什么、没做到什么

📌 **本节写于缺陷未修时；2026-09-22 已修（BUG-10）**。下表的 ❌ 那一行现已 ✅，
但**修法与下方 §5.7 的推荐方案不完全一样**——见 §5.7 的补充说明。

| | 未修时 | 现在 |
|---|---|---|
| **插件之间**互相隔离 | ✅ 成立（一插件一 `Lua` 状态，§2） | ✅ |
| 插件**报错**不带走宿主 | ✅ 成立（chunk 用 `pcall` 包着跑，§7） | ✅ |
| **"插件能做的事 = 清单申请到的事，没有旁路"** | ❌ **不成立**，旁路就是 `os.execute` 这么宽的东西 | ✅ **成立**——`io`/`os`/`package`/`require`/`loadfile`/`dofile`/`debug` 全部为 `nil`，有 4 条用例钉着（`docs/06` §6.1 `lua::tests`） |
| 插件**撑爆内存**时宿主不倒 | ❌ 不成立（§6） | ❌ 仍不成立 |
| 插件**死循环**时宿主不倒 | ❌ 不成立（§6） | ❌ 仍不成立 |

**未修时的准确定位是**：Nota 的插件**是"用户信任的代码"，与 Folio 的 `.so` 插件
处在同一个信任级别**——区别只在**故障隔离更好**，**不是安全隔离更好**。
这个定位现在变了：**故障隔离与安全隔离都成立**，但**后两项（内存、死循环）仍不成立**，
所以"插件是受信任代码"这个结论**只对这两项成立**。

### 5.7 修法（本文件原只记录、不动源码；2026-09-22 已按下面的 A+ 落地）

| 方案 | 怎么做 | 代价 |
|---|---|---|
| **A. 把那几个库真从掩码里摘掉** | `Lua::new_with(StdLib::STRING \| StdLib::TABLE \| StdLib::MATH \| StdLib::COROUTINE, …)` —— 显式列白名单，不用 `ALL_SAFE` | ⚠️ **`require` 会一起没**（`require`/`package`/`loadlib` 都不在）。今天两个内置插件都是单文件，**所以今天没有代价**——但要提前知道这个取舍 |
| **B. 保留 `io`/`os`，改文档与能力表** | 承认"插件是受信任代码"，能力表只描述宿主 API 的可见性 | 诚实，但**放弃沙箱叙事** |
| **C. 换到独立进程 / WASM** | 副作用全部绕回宿主 | 工程量大，且与"Lua 直接调宿主 API"的简洁**直接冲突** |

#### ⚠️ **A 单独用是不够的——实测推翻了本节的推荐**

本文件原本推荐 A。落地时补测了一次，**发现 A 有漏**：

```text
只做 A（列白名单、不额外抹任何东西）之后：
  io / os / package / require / debug   → nil      ✅ A 挡住了
  loadfile / dofile / load              → ★ 还在   ⚠️ 没挡住
```

原因：**`loadfile`/`dofile` 属于 base 库，而 base 库 mlua 是*无条件加载*的**
（`print`/`pcall`/`setmetatable` 都在里面，没法通过 `StdLib` 关掉）。后果实测：

```text
loadfile("/etc/hostname")        → 错误信息里把文件内容漏了出来
                                   （syntax error 会引原文那一行）
loadfile("/tmp/mlua-evil.lua")   → ★ 加载成功并执行了磁盘上任意 .lua
```

所以 A **单独**用，插件仍然能读并执行磁盘上的任意 `.lua` 文件——比 `os.execute` 窄，
但仍是实实在在的旁路。**真正的修法是 A + 显式抹除**：

```rust
// src-tauri/src/lua/mod.rs
fn 插件标准库() -> mlua::StdLib { /* COROUTINE | TABLE | STRING | UTF8 | MATH */ }

const 必须为空的全局: [&str; 7] = [
    "io", "os", "package", "require",
    "dofile", "loadfile",   // ← base 库给的，白名单关不掉，必须显式置 nil
    "debug",
];
```

**⚠️ 这条补充是本文件最值得记的一句**：**别信"列了白名单就安全了"**——
库会**无条件**给你一些你没要的东西，而 `StdLib` 那种按位掩码的接口**表达不了
"我要 base 库但不要 `loadfile`"**。列完白名单之后必须**把结果再验一遍**，
这正是 `docs/06` §6.1 里 `沙箱里不该有的全局一个都不能有` 那条用例的由来。

### 5.8 想自己复核一遍

探针的全部内容就是一个 `Cargo.toml`（依赖那一行与 `src-tauri/Cargo.toml` 的 `mlua = …` **逐字相同**）
加一个 `main.rs`（`Lua::new()` + 一个把 `type(_G[...])` 收集成表的 chunk）。
在本机的 `tauri-dev` 容器里建一个临时 crate（`docs/06` §2 讲了怎么进容器），
`cargo run --offline` 即可。**别用 `--online`**：容器里没有网络。

⚠️ 注意 `--offline` 要求 registry 里已经有 mlua 0.12.1——跑过一次 `cargo build`
就有（`docs/06` §2 的构建命令会把它拉下来）。第二个坑是**文件属主**：
容器里以 uid 0 写的文件，uid 1000 的 `cargo` 改不了（`docs/06` §2 那张 uid 表）。

## 7. 故障隔离：现在实际做到了什么

这些机制**是真的在工作**的，别因为 §5 就以为整个运行时不可信——
它们是"错误隔离"，不是"故障隔离"（§6）。区别很重要。

| 机制 | 在哪 | 效果 |
|---|---|---|
| 入口 chunk 用 `eval()` 跑，错误折成 `state = Failed(原因)` | `lua/mod.rs` 的 `run_entry()` | Lua 语法错 / `on_load` 抛错 → 这个插件标红，**宿主照常启动** |
| `load()` **不返回 `Err`** | `lua/mod.rs` 的 `LuaPlugin::load()` | 一个插件坏掉不该让整个启动流程挂掉。理由很实在（`src-tauri/src/plugin/mod.rs` 的「一个插件坏掉不能拖垮启动」那一节）：**让一个写错的 Lua 脚本变成"应用打不开"，用户连去禁用它的界面都进不去** |
| `on_unload` 的报错**只记不抛** | `lua/mod.rs` 的 `unload()` | 卸载流程不被一个插件的残骸卡住 |
| 撞名插件走 `rejected()`，不另造状态 | `lua/mod.rs` 的 `rejected()` | 两种失败对界面来说长得一样（一行标红 + 一句原因） |
| 模块表存 **registry** 而不是 globals | `lua/mod.rs` 的 `run_entry()`/`unload()` 里那对 `nota_module`、`api/mod.rs` 里那对 `nota_commands` | ⚠️ 理由：**插件可以合法地把全局 `nota` 覆盖掉**，所以宿主自己的东西不能放在会被借走的名字下 |

⚠️ **"错误隔离"的边界在哪**：`pcall` 抓得住 Lua 的 `error()`、
抓得住 `attempt to index a nil value`，**抓不住** `os.exit()`、进程被 OOM 杀掉、
C 层 abort。§6 那几条之所以是"没实现"而不是"不会发生"，就是因为这个边界。

## 8. 一张图收尾
